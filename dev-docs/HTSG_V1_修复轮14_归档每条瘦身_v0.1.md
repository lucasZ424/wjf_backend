## 2. 每条记录：现在与改后

**现在：** 每个输入值在 `observation` 写一行 25 列（记录 ID、提交组 ID、运行 ID、来源、通道名、质量、来源类型、原记录 ID、轮询 ID、应答 ID 等文本；连接代次、段号、批次号、批内序号、轮次号；收到时刻、单调时钟、源时间戳、重申时刻两个、生效时刻；值、状态码、极值、桶号），另有 5 个索引。派生值在 `result` 写一行，另带 JSON 格式的计算依据、估算明细和 64 位配置 ID。Modbus 每轮另在 `state_event` 写一条带 JSON 的轮询记录。

**改后：** 输入值与派生值共用一张 `sample` 表，每行 9 列，1 个索引：

| 列 | 类型 | 字节 | 用途 |
| --- | --- | --- | --- |
| 桶号 | int4 | 4 | 分区与滚动删除 |
| 时刻 | float8 | 8 | 生效时刻（补写的行用补写时刻） |
| 值 | float8，可空 | 8 | 非良好质量时仍保留设备给的值 |
| 运行号 | int4 | 4 | 回放按段判定有效至、断线 |
| 段号 | int4 | 4 | 同上 |
| UA 状态码 | int4 | 4 | 32 位无符号按补码存，读出还原；非 OPC UA 的行写 0、不写空（审核第1条） |
| 通道号 | int2 | 2 | 由本库 `channel` 表解释 |
| 状态 | int2 | 2 | 质量、未取得原因、派生不可用原因；另一位标超出物理极值 |
| 批内序号 | int2 | 2 | 同一批里同一点有多条 OPC UA 通知时共用收到时刻（终版第10节第2条），靠它排先后、认出批末值（审核第1条） |

索引：（通道号，时刻）。按 PostgreSQL 存储格式推算：没有空值的行表里 68 字节，加索引约 95 字节；值为空的行（未取得、不可用）行头多出空值位图，表里 76 字节。都未实测（第7节实测）。

## 3. 修改方案

### 3.1 表结构（`htsg/archive_schema.sql`，库代数 6→7）

- 删 `observation`、`result` 两张表，新建按桶分区的 `sample`（第2节）。`PARTITIONED` 改为 `commit_group`、`sample`、`state_event`；`prepare_bucket`、`retire_bucket`、`bucket_bytes` 跟着改。
- 新增 `channel`（编号 smallint ↔ 通道名＋来源，唯一键为通道名＋来源）；`run` 加整数编号。两者每个库各自编号，读时只用本库的表解码，主库与应急库不必一致。
- 新增 `state_code`（编号、代码、中文含义），建库时由程序内的转换表写入。
- 新增视图 `sample_view`：本地时间、通道名、来源、值、中文状态、十六进制 UA 状态码、是否超出极值，供技术人员直接查库。
- `state_event` 只写保留边界基线（回放只读这一种）；段起止、缺口、水位、运行结束、故障丢失照旧写进各自的小表。成功的轮询轮次不再留记录；失败的轮次本来就有“未取得”的数据行。
- `commit_group` 保留：整批写入与重试不重复靠它（同一组再写时返回“已写过”，组内成员不再写）。

### 3.2 写入（`htsg/archive.py`，状态转换表在 `htsg/records.py`）

- 内存里的观测与派生记录照样生成，写库时只取第2节的列。
- 质量（良好、不良、不确定、各种“未取得”）与派生原因转成状态编号；超出物理极值占一位；计算异常的自由文本一律记为“计算出错”。
- 通道号、运行号在同一事务里查，查不到用 `INSERT … ON CONFLICT DO NOTHING` 插入后再查一次（同现有 `run` 的写法，不让一次唯一键冲突使整组写入失败；审核第5条）；事务提交成功后才放进本库的缓存。
- 批内序号取内存记录原有的批内序号（每批从 0 数起，一批最多约 2000 条）；派生行写 0。保留基线的记录在内存里是 `BASELINE_ITEM`＝2³¹−1（`htsg/owner.py:113`），装不进 int2，写库时记为 32767（仍排在同批之后）；`-1` 照写。写库前统一限在 int2 范围内，不让一个越界值使整组写入失败。
- `group_span` 与桶的时间范围更新不变。

### 3.3 回放读取（`htsg/history.py`）

- 查询改为 `sample` 关联 `channel`、`run`，还原出通道名、来源、运行 ID、段号、质量、状态、原因；段、水位、缺口、保持值、行数上限的拼接逻辑不动。
- 同一通道的行按（时刻，批内序号）排序（原来按批次号与批内序号）。
- 主库与应急库的结果直接拼接，不再按行 ID 去重（`_all`、`_search` 两处）。不会重复的依据：一组首次写入后，重试只发往同一个库（`archive_router` 的锁定），保留基线在每个库里是各自的行（审核第3条）。
- 解码遇到本库对照表里没有的通道号、程序里没有的状态编号时，该行显示为“未知”，不抛异常（审核第5条）。

### 3.4 接口（`htsg/history_api.py`）

- 删 `/api/replay/basis` 与 `history.input_basis`（页面从未调用）；重新生成 `docs/openapi.json`。

### 3.5 前端（`htsg/static/replay.js`、`htsg/static/app.js`）

- 回放表去掉“原观测时间”“批次与序号”“来源”三列；“窗口起点依据”不再写原观测时间与来源。
- 缺口标记只保留“终于缺口”，去掉“缺口后重申”。
- 导出去掉对应 5 列（原观测时间、原观测时间(UTC秒)、批次号、批内序号、来源），改写“保持值”的说明。
- 实时页、故障页、自检页不动。

### 3.6 脚本

- 部署与建库脚本跟着第 7 代改。

## 4. 定下的取舍

1. **同一通道的先后按时刻排，同一时刻再按批内序号。** 段内墙钟回拨不到 2 秒时，相邻两批的行可能颠倒；超过 2 秒，程序本来就新开一段。接受。同一批内的先后由批内序号保证（审核第1条）。
2. **故障记录表不动。** 其中“依据记录 ID”以后指向不存在的行；页面不用这一列，表很小，以后再清理。
3. **计算异常统一为“计算出错”**，原文不存。
4. **通道号、运行号每个库各自编号**，靠本库的对照表解码（不用按名字算哈希，那样每条多 4 字节）。
5. **桶号保留。** 按天分区可以省掉这一列（每条约省 8 字节），但要改掉桶机制，还要处理时钟回拨写进已封存或已删除的分区。

## 9. 实施与结果（2026-10-31）

### 9.1 与第3节的差别

- **运行号**放在单独的 `run_number` 表（编号、运行 ID），不在 `run` 表加列：`run` 的配置 ID 与启动时刻必填，写一行数据时不一定都有。
- **通道号、运行号**不用序列，在写入事务里取本库最大号加一：事务回滚不耗号，号不会因反复失败而用尽。
- **`commit_group.records`** 改为该组写进 `sample` 与 `state_event` 的行数。数据行不再带组号，整组是否写全改为按库清点：各组声称写了几行，对比库里实际几行。`scripts/verify_resilience.py` 的检查随之改为“缺行数／多余行数”。
- **程序不认识的状态码**：输入范围内读作“未知”，派生范围内读作“无法识别的状态”（`UNKNOWN_STATE`），不抛异常。
- **`state_event` 只写保留边界基线。** 时钟跳变标记（跳变量、此前被丢弃的标记数）因此不再入库，库里只留它切开的有效段。第3节没有提到这一项；用户 10-31 定：不存。

  - **重写的用例**：整组写入、崩溃不留半组、停机次序、回放语义、滚动删除、跨库合并等规定仍在、只是按旧表写的用例。改用共用的 `tests/archive_support.py`：按库清点行数；通过 `sample` 与对照表读数据；运行的开始与结束从运行级的组认出；重申的值认作从所在有效段起点生效的那一行。
