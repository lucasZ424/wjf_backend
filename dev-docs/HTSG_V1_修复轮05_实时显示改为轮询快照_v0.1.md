## 1. 问题与用户裁定

核实（读代码，未改源码）：

1. **推送任务不在监督之内（审核第7条）：** 推送任务由 `web.py` 的 `lifespan` 单独创建，没有挂核心任务的结束回调。它一旦结束：
   - owner 每处理一批仍向 `pending` 追加一条；`pending` 只在推送循环里和新页面连入时清空，没有页面打开时会无上限增长。
   - 已打开的页面3秒后显示“消息中断”，但不会自己重连，一直停在旧数值上。
   - 采集和归档照常进行，health 看不出异常。
   
   推送循环里可能抛异常的只有两处：拼状态（`owner.status()`）和放入页面出箱，都只读写内存。现有代码里没有找到能让它抛异常的输入；现有实测里实时推送累计约1.6小时、最长一次10分钟，推不出频率。
2. **推送编码位于归档提交之前（清单外）：** owner 处理一批时，`_emit` 先调用推送（`_publish` → `publisher.offer`：重算417个量的视图、比差异、编码），再提交归档（`_submit`）；从 ingress 到 owner 循环这条路径上没有异常处理。推送编码一旦抛异常，这一批不进归档，异常结束 owner 循环，后端退出、由守护脚本重启。

评估过、未采用的修法：

- **推送任务出错即退出、由守护脚本重启：** 收回。这类异常若出现，多半由某种持续存在的状态触发，重启后几秒内就会重现。守护脚本两次启动之间依次等5、10、20、40秒，之后60秒，连续运行满10分钟才复位。若缺陷在启动后30秒内重现，稳态约每1.5分钟重启一次、每天约900次，采集约三分之二的时间停着。（经监督退出是受控停机，运行以 `NORMAL` 收尾，不是 `ABNORMAL_EXIT`。）
- **两层修补（推送循环内部恢复＋页面看门狗重连）：** 可行，但推送任务、待发队列和连续性协议都还在，被下面的方案取代。

用户裁定（2026-10-27）：

- **实时显示改为页面每秒通过 HTTP 读取一次完整当前状态，替代 WebSocket 推送，作为正式方案；后台继续按批次采集、计算和归档。** 理由（用户要点）：业主已明确1秒刷新足够、平时不会经常查看，实时趋势的过程保真权重大幅降低；这样长期运行需要维持的状态和恢复分支最少。
- 具体行为（用户的5条）：
  1. 后端提供只读快照接口：同步读取 owner 当前的417个通道及质量、有效性、原观测时间和故障状态，不查询数据库，也不等待新数据。
  2. 网页目标每秒请求一次，全应用共用一个轮询；同时最多一个请求，前一个没结束就跳过本轮，不补发、不积压；请求最多等待5秒，超时取消，随后继续尝试。
  3. 成功就整体替换当前显示；不维护增量队列，不补丢失消息，不需要序号连续性修复；故障恢复后的第一次成功响应就是新的完整当前状态。
  4. 连续3秒未取得成功响应，页面标明中断；旧值不能继续呈现为正常的当前读数；恢复后自动更新并清除提示；网络故障和服务暂时不可用都自动重试，无须刷新页面。
  5. 采集归档不调用页面编码和发送：从 owner 处理批次的必经路径中移除实时投递，快照读取发生在 HTTP 请求里；一次显示请求失败，不应中断采集或本批归档。
- 实时曲线按这些快照绘制，精确过程到历史页查询；通信·日志页原有的5秒查询、历史查询和账户管理保持原方式。用户接受的代价：每秒传输全量状态，一秒内的短暂变化可能不出现在实时图上。
- **每个请求照常鉴权，不加凭据缓存；删除推送专用配置字段；先出终版与实施方案的改写草稿给用户审，再写测试、改代码。**
- 草稿审阅的意见与确认见第3节开头。

## 2. 评估数据与实现约束

评估数据（2026-10-27，本机；测量脚本在会话临时目录，不入库）：

- **快照：** 研究配置417个量每秒都变时，一份完整状态约154 KB（JSON）。owner 生成0.18毫秒（中位），`json.dumps` 0.9毫秒；经 FastAPI 默认的字典返回（`jsonable_encoder`）要5.5毫秒。现行推送每组0.23毫秒、满量每秒2组，在 owner 的调用里执行，没有页面打开时也照样执行。
- **鉴权：** 每次请求做一次 scrypt（n=2^14，r=8），约34毫秒 CPU、16 MiB 临时内存，在工作线程里执行，最多同时4个。连续校验时，事件循环的唤醒延迟不变（p99 15.4 → 17.4毫秒，在 Windows 定时器粒度之内）。每秒轮询时，每个打开的页面约占本机一个核的3%；现场机器未测。被页面放弃的请求在服务端照样很快做完，总并发由 uvicorn 限制在32，不会堆积。
- **显示延迟：** 现行从实收到绘制 p99 约125毫秒（修复轮04 的 G3）。改后取决于轮询相位、采集等待、鉴权、请求和浏览器调度；1秒是轮询的目标周期，不是延迟上界。

实现约束（由上面的规则和代码推出）：

- 快照接口写成 `async def`，在事件循环线程里一次读完，截取过程不 `await`。不能写成普通 `def`：FastAPI 会把它放进线程池，和 owner 同时读写同一批字典。返回已序列化的 JSON，不走 `jsonable_encoder`。
- owner 的推送出口换成空操作。owner 只在输入通道视图里补上当前观测的ID这一项（测“新观测实收到显示”要用），其余不改，提交组、发布组的语义和相关测试照旧。删除推送任务、`publisher.py`、`stream_api.py` 和 `/api/stream`。
- 观测ID的含义（已核对 `records.py` 与 `owner.py`）：一条观测的 `id` 稳定；状态重申是另一条记录，`origin` 标为重申、`orig_id` 指向原观测，`received_wall` 保留原观测时间。所以“新观测”按“实收且ID首次出现”判定，重申不会冒充新采样。
- 服务端已有并发上限32，访问日志已关闭（`cli.py`），每秒的请求不会增加日志。
