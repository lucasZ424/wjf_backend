## 2. 机组模型（`htsg/simulation.py` 的 `Plant`）

660 MW 超超临界直流炉；600 MW 称“参考工况”，下列关系都相对它计算，只用于中高负荷，不外推到启动与深度低负荷。所有惯性是一阶惯性的**时间常数**（阶跃后该时间达到 63%），不是延时后突变。数字是演示设定，不是真实机组的保证值。

| 量 | 跟谁走 | 时间常数 |
| --- | --- | --- |
| 负荷 | 600 MW ± 8 MW（40 分钟周期）＋ 3 MW（15 分钟）＋小幅漂移；约 588–612 MW | 10 s |
| 水冷壁流量、主汽流量 | 正比于负荷（参考 1850、2117 t/h）；水冷壁流量不低于参考的 55%（直流炉最小流量） | 20 s |
| 主汽压力 | 28.7＋0.02×(负荷−600) MPa（局部演示关系；真实滑压曲线由控制策略决定） | 60 s |
| 给水温度 | 309＋0.1×(负荷−600) ℃ | 300 s |
| 工质、再热温度 | 435、623 ℃，变负荷时偏离 0.3、0.2 ℃/(MW/min) | 120 s |
| 炉膛负压 | −0.05 kPa 附近湍动 | — |
| 内壁温度 | 该高度工质温度（入口＝给水＋51 ℃，出口＝工质温度，按段线性）＋膜温差 40 K×局部热负荷÷(流量比^0.8) | 90 s |
| 外壁温度 | 内壁＋导热温差 30 K×局部热负荷 | 90 s |
| 电桥 | 参考应变（118…174 με）＋20 με/K×温差相对参考的变化＋24 με/MPa×压力相对参考的变化，再按 Bridge＝ε×6/1000 反算 | — |

- 局部热负荷＝段份额（H1…H8：0.55、0.8、1.0、1.0、0.9、0.75、0.6、0.45，燃烧器区 H3–H4）×周向不均（±3%，固定）×负荷比×（1＋局部超温加热）。段号与组号沿用模拟通道分配：编号 i 的段为 `(i−1)%8+1`。
- 测站 n（S0n）对应温度对 n 与电桥 n。
- 发送分两档（`htsg/simulation.py` 的 `NOISE` 表）。**演示档**：小幅相关噪声（每秒保留 95%），温度、负荷、流量按 0.1 取值，压力 0.001；稳态下壁温约 37% 的秒有变化，全场平均每秒约 85 个点变化。**稳态档**：噪声更小更慢（温度每秒保留 99%），再加死区——量离上次发出的值满一个台阶才发新值（壁温 0.1 ℃、负荷 0.5 MW、流量 2 t/h、压力 0.01 MPa、电桥 0.0006 mV/V 即 0.1 με），稳态下壁温平均约 99 秒变一次、电桥约 42 秒、负荷与流量约 20–30 秒，全场平均每秒约 3 个点变化。两档物理关系、场景、越限相同。
- 模型没覆盖的点（点表工具在模板外新加的点）仍按各自信号发数。

## 3. 场景（`config/research-sim.json`）

| 名称 | 标签 | 做法 | 预期越限 |
| --- | --- | --- | --- |
| `baseline` | 恢复正常基线 | — | 无 |
| `load_ramp` | 变负荷 | 从当时负荷按 12 MW/min 到 510 MW，保持，再按同速率回到基线摆动；1200 s | 无 |
| `hotspot_01` | 测点01局部超温 | 温度对 01 的局部热负荷升到 4 倍（加热 3.0）；壁温按 90 s 惯性升、结束后按同样惯性回落；600 s | 外壁温度高（490 ℃）、内外壁温差负向（LOW，−55 ℃）、应变负向（−690 με） |
| `overload` | 超负荷 | 同变负荷做法，目标 690 MW；1200 s | 主汽压力高（30 MPa）、主汽流量高（2223 t/h）；负荷不到 693 MW 高限，壁温不到 490 ℃ |
| `extreme_temperature` | 测点01内壁温度传感器极端值30秒 | 原样（内壁＋500 ℃） | 极端值，依赖它的派生量不可用 |
| `bad_quality`、`freeze`、`disconnect_modbus`、`disconnect_opcua` | 原样 | 原样 | 原样 |

- 原 `thermal_step`（测点01壁温阶跃）、`load_cycle`（逐点偏移的半正弦）两个场景去掉，由 `hotspot_01`、`load_ramp` 代替；场景种类 `load_cycle` 去掉，`thermal_step` 种类留作“加偏移”（极端值场景用）。
- 热应力代理没有业务越限阈值，不产生故障记录；负温差加大时它更负、绝对值增大。符号只表示温差方向，不能解释为真实的拉应力或压应力。

## 4. 两档与写入上限压测

- 演示档：`python -m htsg.simulation`（默认）、`research_lab.py run`、模拟包“1-启动模拟现场（演示）”。
- 稳态档：`python -m htsg.simulation --steady`、模拟包“1-启动模拟现场（稳态）”。
- 写入上限压测：只有开发脚本 `scripts/measure.py`、`smoke.py`、`verify_resilience.py` 用（`FieldSimulator(..., write_ceiling=True)`），没有命令行开关，不进任何包。208 路按各自信号（`simulation.signals`，即原有的独立正弦加白噪声）发数，每秒全部变化——修复轮14 实测 4.1 GB/天就是这个量。真实机组不会这样；它代表网关把带噪声的原始值直接送上来时后端可能承受的最大写入。工艺场景在此被拒绝，故障类场景照常。

## 5. 后端与前端

- `htsg/config.py`：运算种类加 `absolute_peak`，单位规则与 `maximum` 相同；`htsg/derive.py`：`max(values, key=abs)`（绝对值相同时取先出现者）。输入无效、极端、缺失时与其他运算一样返回不可用，不抛异常。
- 两份配置的 `thermal_stress_peak` 改用 `absolute_peak`，标签改为“热应力代理绝对峰值（保留符号）”；点表工具把它当作多输入派生量（缺的输入去掉、剩下的照算）。
- `htsg/static/app.js`：热应力页三栏与历史回放图的纵轴按量设最小跨度，刻度取 1、2、5×10ⁿ 的整齐步长；数据超出最小跨度时照数据放宽，越限照样显示。最小跨度：温差 10 ℃、壁温等其余 ℃ 20、热应力（代理与峰值）10 MPa、其余 MPa（压力）1、MW 50、t/h 100、kPa 0.2、με 50、mV/V 0.05。热应力取 10 MPa（不是方案示例的 2 MPa），使它与温差栏（系数约 1.15 MPa/K）的观感一致。
- 曲线分色（用户 11-01：统一颜色不好看）：按量的种类着色，趋势与回放同一套——负荷及其余量蓝 `#73bcff`、内外壁温差青绿 `#4fd1a5`、热应力（代理与峰值）紫 `#c79bff`；热应力页图中栏名与上方读数的名称用同色当图例。红色仍只表示“无数据”，琥珀色仍是游标与缺口，曲线不用这两色。`test_web_trend.py` 的像素检查改为按各栏自己的颜色数（原来只认蓝色，分色后温差、热应力两栏的“缺口里没有线”会恒真），并新增“三栏三色、每栏都按本色画出”。
- 越限换色（用户 11-01 选“趋势加回放阈值着色”），橙色 `#ff9f43`：
  - 热应力页趋势：该量“故障已确认”期间的曲线画橙色（按后端快照里的越限状态；“越限待确认”不变色），复归后回到本色。热应力代理没有业务阈值，那一栏不会变橙。图下说明写明“曲线变为橙色表示该量‘故障已确认’”。

## 6. 傻瓜式安装

**免安装运行环境**（`tools/release/runtime.py`）：构建时把构建机的 Python 3.13 x64 拷成 `runtime\`（去掉文档、测试、tkinter/IDLE、头文件、构建机自己装的第三方包），用离线依赖把程序与全部运行依赖直接装进去。`python313._pth` 只列 `DLLs`、`Lib`、`Lib\site-packages`，不 `import site`：现场电脑上另装的 Python、`PYTHONPATH`、用户目录的 site-packages 都进不来（演练时发现带 `import site` 会把 `%APPDATA%\Python\Python313\site-packages` 加进来，已去掉，构建自检会查）。现场不装 Python、不建 venv、不跑 pip、不写注册表。

**VC 运行库**：免安装版 PostgreSQL 依赖 `VCRUNTIME140.dll`、`VCRUNTIME140_1.dll`、`MSVCP140.dll`（postgres 与 ICU 库），压缩包里没有，干净 Windows 也没有——开发机装过 VC 运行库所以一直没暴露。构建时从构建机 System32 拷入 `installers\vc\`，安装时放进 `pgsql\bin`（应用本地部署）。

**一键安装**（`tools/release/install.py` → 包内 `setup\install.py`；入口 `安装.cmd`，纯英文三行：没有管理员权限就请求提权，再用包里的运行环境运行安装程序）：核对 SHA256SUMS → 拷程序到 `<根>\app` → 解压 PostgreSQL 到 `<根>\pgsql` 并放 VC 运行库 → 放配置（参数、发布包旁边的 `production.json`、或提示拖入）并核对 → 选两块数据盘（列出本地硬盘与剩余空间，默认最大的给正常库、次大的给应急库，两块不能相同）写 `deploy.json` → `deploy_databases.py plan/install/register/status` → 等后端响应、打开浏览器。可重复运行：做完的步骤跳过；拷贝与解压先写到 `.partial` 目录再改名，中途断电重跑时重做；已装另一版本、已有配置与部署文件都不覆盖；安装目录有中文或空格时一开始就停（PostgreSQL 处理不了）。日志追加到 `<根>\install.log`。也可无人值守：`--root --config --primary --emergency --yes`。

**点表工具包**（`HTSG-POINTSHEET-…`，`build_release.py` 一并构建）：运行环境＋`pointsheet.py`＋`launch.py`＋生产基础配置；“1-生成点表模板”（已有 `点表.xlsx` 不覆盖）、“2-生成配置”（把点表拖上去；通过才把旧的 `production.json` 改名留底再写新的，不通过旧的不动）。

**模拟数据源包**：自带运行环境；“1-启动模拟现场（演示）”“1-启动模拟现场（稳态）”“2-触发场景”（按编号选）；`production.json` 放在包顶层，安装时交给安装程序。不再需要拷进程序目录。

**入口文件为什么是纯英文**：cmd 按系统代码页读批处理，中文内容容易乱码；所以 `.cmd` 里只有英文，中文提示都由 Python 输出，文件名可以是中文。

发布包、点表工具包、模拟包里不再带 `wheelhouse` 和 Python 安装程序；`build_release.py` 去掉 `--python-installer`，没有 PostgreSQL 压缩包时拒绝构建。
