# HTSG V1 满量测量与容量报告

版本：v0.1｜日期：2026-10-12｜依据：[开发实施方案](HTSG_V1_开发实施方案_v1.0.md) D46、D47，[终版设计](HTSG_V1_终版设计_v1.0.md) 第 13.4–13.5、16 节。本文只记录实测事实和由它直接算出的数；是否“够用”的结论只写到能由数据支持的程度。

**这是什么环境的数据：** 一台开发笔记本（Windows 11，Python 3.13.4），后端、独立研究模拟器（8 路 Modbus Bridge＋200 个 OPC UA 监控项）、两个 PostgreSQL 18.6 开发实例、Chrome 全部在同一台机器上，走本机回环，没有对 CPU 做隔离。数据来自模拟器，不是现场设备。**没有真实设备、真实 OPC UA 网关、独立卷和磁盘的数据，下列结果只能说明模拟环境，不能证明现场投运或一年容量。**

## 1. D46 满量协议与性能测量

命令：`python scripts/measure.py --steady 180 --outage 25 --browser --out docs/evidence/d46`；原始数据 `docs/evidence/d46/measure-20261012-190141.json`。工具在产品代码之外取时间戳（包住提交、发布与发送入口，页面里包住 `WebSocket` 与 `requestAnimationFrame`），产品代码未改动。测量库是脚本自己建、自己删的 `htsg_perf_*`。

### 1.1 初值突发（系统启动到全部有效）

| 项 | 实测 |
| --- | --- |
| 从启动到 417 路全部有效 | 1.4 秒（含连接、订阅 200 个监控项、打开归档） |
| 归档追平（所有已交出的组都已落库） | 0.06 秒 |
| 提交队列峰值 / 入口峰值 | 2 组 / 0 批 |
| 事件循环最大迟到 | 14.8 毫秒 |
| 未解释的丢失 | 入口丢弃 0、队列拒绝 0、策略拒写 0、写入失败 0 |

### 1.2 稳定满量（180 秒）

模拟器每秒改变全部 208 路输入（是上界：现场多数量并不每秒变化），后端据此每秒产生 209 路派生量。

| 项 | 实测 |
| --- | --- |
| 已发布 / 已提交的组 | 360 / 394（多出的 34 组是状态、水位等不发布的组） |
| 提交吞吐 | 418.0 行/秒，2.19 组/秒 |
| 落库字节 | 336,690 字节/秒（数据库大小的实测增量，含索引）；路由的保守估算为 714,946 字节/秒，是实测的 2.1 倍 |
| 提交队列深度 | 中位 0，p99 1，最大 3（容量 400） |
| 入口队列深度 | 最大 1（容量 4096） |
| 提交等待（交给队列到落库确认） | 中位 22.6、p95 62.8、p99 89.6、最大 161 毫秒 |
| 事件循环迟到 | 中位 4.5、p95 9.6、p99 14.6、**最大 272 毫秒** |
| 维护（重型统计，本次每 5 秒一次，默认 60 秒）占用写入线程 | 最大 0.293 秒；不在事件循环上 |
| 内存（本进程工作集） | 154.3 → 165.6 MB（180 秒涨 11.3 MB，含测量工具自身的记录；**未证明持平**，需更长的运行才能断言没有泄漏） |
| WAL 峰值（整个实例） | 112 MiB |
| 结束时队列里未写入的组 | 0；测量结束后追平耗时 0.0 秒 |
| 未解释的丢失 | 全为 0 |

### 1.3 断连恢复

协议一侧消失 25 秒后恢复，各一次：

| 数据源 | 发现断开 | 恢复后重新全部有效 | 归档积压清空 | 重新同步次数 | 归档状态 |
| --- | --- | --- | --- | --- | --- |
| OPC UA（`ua_field`） | 0.45 秒 | 15.4 秒 | 0.11 秒 | 1 | 两源均正常，无缺口 |
| Modbus（`mb_field`） | 0.58 秒 | 10.7 秒 | 0.06 秒 | 1 | 两源均正常，无缺口 |

“恢复后 10–15 秒”是重连退避（1 秒起翻倍，上限 30 秒，稳定运行满 60 秒才清零）的结果：断了 25 秒，退避已走到 8–16 秒的间隔，下一次尝试落在对方恢复之后。这是终版第 11 节的设计，不是故障。

### 1.4 推送延迟：后端实收到浏览器画完

真实 Chrome 打开第 4 页（三分栏画布，是页面里画得最重的一页），453 个组。“画完”指该消息之后第一个动画帧的页面脚本执行结束（含 canvas 绘制调用），不含合成器上屏。各段分别报告：

| 段 | 含义 | 中位 | p95 | p99 | 最大（毫秒） |
| --- | --- | --- | --- | --- | --- |
| 后端内部 | 该组最早一条输入的实收时间 → 组被提供给发布器（轮内等待与组装） | 0.7 | 4.8 | 6.1 | 6.7 |
| 100 ms 合并等待 | 组被提供 → 含它的消息发出 | 101.8 | 109.8 | 111.4 | **330.5** |
| 发出到画完 | 消息发出 → 页面画完 | 11.6 | 14.0 | 15.8 | 43.0 |
| **总计** | 实收 → 画完 | **114.0** | **124.5** | **128.8** | **334.5** |

合并等待的中位数就是 100 毫秒：稳定的一秒一变的输入，每个组都要等满一个合并窗口才发出，这是 100 毫秒合并的预期代价。**最大 330 毫秒超过了“至多 100 毫秒”的字面设想**：打包由事件循环上的定时器触发，循环被占用时它就晚发，上表的事件循环最大迟到 272 毫秒与此相符。占用循环的是什么没有查明（候选：垃圾回收、写入线程持有解释器锁的片刻、重型统计的结果入库），本报告不下结论。用户若要把 100 毫秒当作硬上界，需要另行定位并整改。

### 1.5 测量范围之外

一个浏览器、一页、同机回环、无隔离、一次 180 秒的运行：没有长时间耐久、没有多客户端并发、没有磁盘接近满载下的行为，也没有真实 OPC UA 服务器按真实频率变化的数据。

## 2. D47 崩溃、存储切换与容量

命令：`python scripts/verify_resilience.py all --kills 6 --phase-seconds 6 --capacity-seconds 120 --out docs/evidence/d47`；原始数据 `docs/evidence/d47/resilience-all-20261012-190740.json`。临时库 `htsg_crash_*`、`htsg_switch_*`、`htsg_cap_*` 用后即删。

### 2.1 崩溃恢复（后端作为独立进程，硬杀）

| 第几次 | 杀的时机 | 杀后库里的组数 | 半写的组 / 孤儿行 | 库里各次运行的收尾 |
| --- | --- | --- | --- | --- |
| 1 | 启动后 0.67 秒（运行登记之前，结构甚至还没建） | 无结构 | 0 / 0 | — |
| 2 | 满量运行中 3.19 秒 | 7 | 0 / 0 | 1 次运行尚未结束 |
| 3 | 1.91 秒 | 12 | 0 / 0 | 上一次已收尾为 `ABNORMAL_EXIT` |
| 4 | 4.33 秒 | 23 | 0 / 0 | 同上 |
| 5 | 1.60 秒 | 28 | 0 / 0 | 同上 |
| 6 | 3.39 秒 | 37 | 0 / 0 | 同上 |
| 末 | 正常启动、运行、Ctrl+Break 停止 | 53 | 0 / 0 | 前 5 次 `ABNORMAL_EXIT`，末次 `NORMAL`；已结束的运行里没有仍打开的有效段 |

崩溃后的历史查询正常（不标部分可用，无归档缺口，两个通道各 16 行原始记录）。杀在提交中或提交确认前的精确位置由 `tests/test_capstone_d.py` 的确定性用例覆盖（事务前、事务中、事务后），本脚本是同一性质的进程级检验，杀的时刻是随机的，不能保证每次都落在事务里。正常停止（Ctrl+Break）后进程退出码是 3 而不是 0：uvicorn 在 Windows 上收尾后会把收到的信号再抛给自己，运行结束登记（`NORMAL`）已写入，这是该组合的已知表现，不是异常结束。

### 2.2 存储阈值（注入读数，不填盘）

通过运行中的整条链路，用注入的磁盘占用读数驱动阈值，每步 6 秒。真实盘没有被写满：被注入的只是读数。

| 场景 | 步骤 | 路由 | 这 6 秒新组落在 |
| --- | --- | --- | --- |
| 含移动盘 | 主盘 40 % | 正常库 | 正常库 12 |
| | 主盘 96 % | 移动库 | 移动库 14 |
| | 主盘回到 40 % | 仍是移动库（不自动切回） | 移动库 12 |
| | 移动盘 96 % | 应急库 | 应急库 14 |
| | 移动盘 80 % | 仍是应急库（回差） | 应急库 13 |
| | 移动盘 69 % | 回到移动库 | 移动库 15 |
| 无移动盘 | 主盘 40 % | 正常库 | 正常库 12 |
| | 主盘 96 % | 应急库 | 应急库 14 |
| | 主盘 80 % | 仍是应急库（回差） | 应急库 12 |
| | 主盘 69 % | 回到正常库 | 正常库 14 |

两个场景里每一步路由都等于预期、新组只落在路由指定的那一个库，各步中两个数据源的归档状态始终为正常，所有者的“归档丢失组数”为 0；三个库里 89 个（61 个）组各只存一份、没有半写的组；跨库合并的历史（含移动盘场景 40 行原始记录、无移动盘场景 27 行）无部分可用、无重复、按序。

### 2.3 一年容量

方法：满量实测日增长乘 365；数据库大小的增量已含索引，故索引不另计；WAL 峰值与维护峰值各计一次（不随年份增长）；再扣磁盘余量（`emergency_reserve_bytes` 默认 100 GiB）。这一步没有做任何估算替代实测。两种输入行为分别量了 120 秒：

| 项 | 每秒都变（208 路输入全变） | 保持静止（所有值恒定） |
| --- | --- | --- |
| 行/秒 | 417.7 | 32.2 |
| 字节/秒（含索引） | 333,335 | 28,431 |
| 字节/行 | 798 | 883 |
| 日增长 | 28.8 GB | 2.46 GB |
| 一年 | **10.5 TB**（10,512,052,560,000 字节） | 0.90 TB（896,600,016,000 字节） |
| WAL 峰值（计一次） | 128 MiB | 128 MiB |
| 可用卷空间（D:，实际读数） | 1.33 TB | 1.33 TB |
| 余量（扣 100 GiB 保留后） | **−9.29 TB** | +326 GB |
| 结论 | **容量不足：一年留存不通过** | 此卷上够，仅限输入真的几乎不变 |

“保持静止”不是零：Modbus 每轮都存 8 行（每秒 8 行），其余是水位、状态与各次运行的段重述。**真实现场的变化速率没有测量，两栏是上下界而不是预测；终版第 13.5 节要求的是满量实测，该口径下一年约 10.5 TB，超出这块卷当前可用空间近 8 倍，因此按终版规定“容量不足不得通过一年留存验收”。**

行宽是主因：满量时 `result` 表每行约 1.0 KB（数据 20.3 MB＋索引 5.7 MB，25,815 行），`observation` 每行约 0.59 KB（7.6＋7.6 MB，25,792 行）；两张表的索引与数据各占一半左右。每行除数值外还带运行 ID、数据源、点位、稳定 ID、配置摘要等文本列，派生结果还带依据和估算的 JSON。终版里“3.3 GB/天”的估算与满量实测相差约 8.7 倍（与静止栏 2.46 GB/天同量级），没有实测支持它用于满量情形。哪些列、哪些索引可以省，属于设计取舍，本报告不改，也不据此宣称通过。

R07之后，Modbus输入每次由有效转为失效，会在原有记录之外多写一条失效观测，满量下一次失败转移最多多8条；输入持续失败时不重复写。因此容量按失败转移的频率计入，不能当成每秒多8条。

### 2.4 未覆盖

没有真实磁盘接近 95 % 的物理行为（只有读数注入）；没有 WAL 在长时间运行里的峰值（只有 3 分钟）；没有重型统计之外的维护动作；一年容量没有真实现场的变化速率；移动盘“独立卷”的校验只在开发模式下验证了数据库身份不同，没有验证两个物理卷。

## 3. 复现

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_db.py start
.\.venv\Scripts\python.exe scripts\measure.py --steady 180 --outage 25 --browser --out docs/evidence/d46
.\.venv\Scripts\python.exe scripts\verify_resilience.py all --kills 6 --phase-seconds 6 --capacity-seconds 120 --out docs/evidence/d47
.\.venv\Scripts\python.exe -m pytest tests/test_measure.py tests/test_resilience.py -q     # 同样的检查，缩短后作为回归用例
```

测量与检验脚本只创建并删除自己带前缀的临时库，不碰已有的开发库和研究库。
