## 0. 当前结论

机械整秒分窗造成空值、跨轮错配与展示滞后，采用批次驱动 Hybrid。仅保证按已接纳批次及有效状态计算，不承诺现场同步采样。已确认：不做 Republish；采用缺口、状态重申与新归档段恢复；应急路由保留原始及派生结果；轻量算子同步成组；取消 derivative，保留连续计划轮次的 strain_change；普通越限与极值分开，故障持续5秒并按回差复归；协议输入仅 Good 且通过其他有效性条件才参与计算。

## 1. 方案一（当前实现）缺陷核验

当前机制：

- 采集按单调时钟每秒一拍（[timing.py](../../htsg/timing.py)）；
- 样本以接收墙钟落入 `floor(t)` 的整秒窗口（`engine.py:184-193`（历史文件已删除））；
- 窗口内**恰好 1 个样本**才有值，0 个记 `MISSING_SAMPLE`，2 个以上记 `MULTIPLE_SAMPLES`，两种情况的值都为空（`engine.py:302-314`（历史文件已删除））；
- 计算要求全部输入质量 GOOD（`calculation.py:24-30`（历史文件已删除））；
- 工作区已把 `window_wait` 固定为 0（[config.py](../../htsg/config.py)，未提交改动）。

探针脚本：会话临时目录 `scratchpad/sim_current.py`。它直接调用真实 `Engine`；第 4 项启动真实 `Runtime`，模拟源开启，存储换成内存桩。

| 编号 | 原主张 | 结论 | 证据 |
| --- | --- | --- | --- |
| S1 | 到达抖动和时钟速率差使窗口内出现 0 个或 2 个值 | **成立；后果是空值，不是重复或跳值** | 同批两点、相位距整秒边界 5 ms、抖动 ±8 ms，600 个窗口中：每点 16% 为 `MISSING_SAMPLE`、16% 为 `MULTIPLE_SAMPLES`，**32% 的派生量不可用**。相位在 0.5 时为 0%。 |
| S1′ | 时钟速率差使问题长期反复出现 | **成立** | 本机实测 `time.time()` 为可调的 `GetSystemTimePreciseAsFileTime`，`time.monotonic()` 为不受校时约束的 `QueryPerformanceCounter`；`asyncio.sleep` 中位过冲 10.8 ms。按两钟速率差 10–50 ppm 推演 72 小时：0.42%–0.54% 的窗口为 0 或 ≥2 个样本，即**每天约 360–460 个坏窗口，成簇出现在相位扫过边界时**。速率差是假设区间，未实测。 |
| S2 | （文档未提及）整秒边界切开一轮 Modbus 顺序读取 | **新发现，静默错误** | 当前适配器每个点单独发一次请求，顺序读取（`adapters.py:88-108`（历史文件已删除））。x 在 0.98 s 读到，y 晚 30 ms：每个窗口都"恰好 1 个样本"，派生量 100% 为 OK，但**100% 把 x 与 y 配成了不同轮次**，没有任何标记。现场若每点读取 10–50 ms、十余个点，一轮跨度可达数百毫秒，边界落在一轮之内的相位占比与这个跨度成正比。 |
| S3 | 固定滞后取帧导致画面滞后约 2 秒 | **方向成立；当前实现典型值约 1 秒** | 真实 Runtime 实测接收到推送 0.989–1.015 s（12 帧，未含网络与浏览器）。原因是窗口必须收齐后才能出帧，所有者又每秒只推进一次（[runtime.py:251-281](../../htsg/runtime.py#L251)）。当所有者节拍与采集节拍分列边界两侧时，理论上可接近 2 s。文档里的"约 2 秒"指被否决的"先写库再读"方案；当前实现约 1 s，**仍不满足"低于 1 秒"**。 |
| S4 | （文档未提及）`window_wait=0` 时，封窗与到达存在竞态 | **静态推断，未实测** | 所有者节拍与采集节拍是两个独立的单调时钟一秒节拍，相位接近。所有者每处理一条入口记录就检查一次节拍；若封窗发生在同一批的中途，余下样本的窗口已关闭，不进任何帧，状态前沿也不推进（`engine.py:174`（历史文件已删除））。原先 0.2 s 的余量已被移除。 |
| S5 | （文档未提及）OPC UA 缓存值每秒按新接收时间重报 | **成立** | 订阅回调只保存最新值，采集循环每秒把全部缓存值按当前时间提交（`adapters.py:134-139`（历史文件已删除））。在源时间不可用的现场，历史中的"真实更新"与"重报的旧值"无法区分。缓存值是否新鲜，只由连接检查和状态通知约束，而 asyncua 自身的陈旧判定被保活计数放大到失效（见 A4）。 |

**小结：** 机械分窗的问题是结构性的。它同时造成空值（S1）、静默错配（S2）和约 1 秒的固有滞后（S3）。调大或调小 `window_wait` 只能在三者之间取舍，不能消除。**取消整秒帧作为计算与展示前提的方向是对的。**

## 2. 方案二（第 1–12 节）缺陷核验

### 2.1 A1–A10 逐项核验

| 编号 | 结论 | 核验依据与修订 |
| --- | --- | --- |
| A1 | **成立，且波及 §6 的补救方案** | OPC UA 规范 5.13.1.2：服务器采样与底层系统的更新周期"usually not synchronized"，并会带来额外的检测延迟。5.11.2.2：多节点 Read 不承诺同一采样时刻，maxAge 允许返回缓存值，且"the Client can make no assumption about which copy of the data will be returned"。因此"一个周期的不确定度上限"没有依据，§6 的"改为周期性 Read，一次请求就是一帧快照"同样不成立（见 B3）。 |
| A2 | **成立** | Modbus 功能码 03/04 一次只能读**连续的** 1–125 个寄存器（二手资料，官方规范原文未取得）。输入地址不连续、超过 125 个或分属不同从站时，§4 的"同一计算的输入放进同一个请求帧"无法满足。§4 把"源"同时定义为连接、请求和批次，会直接改变看门狗与"同源校验"的作用范围。 |
| A3 | **部分成立** | 机制属实：单循环串行时，计算会拖住原始值推送。但现有算子（差值、线性电桥换算、热应力代数式）都是微秒级，按现有算子集风险低。真正的问题是把"100–150 ms"写成了事实而非实测指标。 |
| A4 | **成立，比原文更严重** | 规范 5.14.1.1：连续 MaxKeepAliveCount 个发布周期都没有通知时，服务器才发保活消息。项目使用的 asyncua 默认 `RequestedMaxKeepAliveCount = int(会话超时 3,600,000 ms ÷ 发布间隔 × 0.75)`，1 s 发布时为 **2700**，即静止订阅可能 **45 分钟**才有一次保活（`asyncua client.py:1279-1280, 1338-1350`（历史本机依赖路径））。按 §7 的 5 秒看门狗，所有静止订阅都会被误判断连。asyncua 自带的 `is_stale` 也按同一计数放大（`subscription.py:475-481`（历史本机依赖路径））。 |
| A5 | **成立，比原文更严重** | 规范 5.14.1.1：重传队列溢出时丢弃最旧消息，客户端可用 Republish 补回。asyncua 只在重连恢复时补缺口（`subscription.py:505-532`（历史本机依赖路径））；会话内收到消息时直接覆盖 `last_sequence_number`，不检查缺口（`subscription.py:267`（历史本机依赖路径））。§7 对缺口只写日志，而 §5 又把"不在批次中"解释为"值未变"。所以对按变化上报的测点，一次丢失的通知会让**旧值被无限期当作有效当前值**，而不是只错一拍。5 秒持续条件也拦不住。 |
| A6 | **成立** | 前半句：OPC UA 输入不变时没有批次，§6 不触发计算，§9 的保活重写又"不触发计算"，所以派生结果的最后一行在 5 s 后过期，回溯时为空，实时显示却有效。后半句：§10 的 SQL 取 g.t 前后各 5 s 内的样本（`stale_after`），不查询 `health_event`，因此会在**宽度不超过约 10 s 的断连或进程重启**两侧做插值。 |
| A7 | **成立** | 数据库慢时，写入队列会积压多个批次，"崩溃最多丢一批"不成立；本地溢写文件的容量、刷盘、回收也未定义。 |
| A8 | **成立** | 规范 7.38.1：StatusCode 是 32 位无符号整数。`smallint`（−32768～32767）放不下；即使 `integer`，Bad 类码（最高位为 1，≥0x80000000）也溢出，`bigint` 才正确。`(point_id, ts)` 主键冲突在微秒时间戳下概率低；但若改用真实墙钟（hybrid 的做法），**校时回拨后新观测会与旧行同键而被静默丢弃**。 |
| A9 | **成立** | 本机实测的单调钟（QPC）不受校时约束。"启动墙钟＋单调增量"相对 UTC 的漂移，按 10–50 ppm 计约为**每天 0.9–4.3 s**，与外部系统（如 DCS 记录）对时会逐日偏离。部署环境为 Windows（`msvcrt` 文件锁、计划任务），而 chrony 没有 Windows 原生发行版。 |
| A10 | **成立** | 208 × 600 = 124,800 个缓冲点，计算正确。存储量按 PostgreSQL 行格式估算：堆约 60 B/行，主键索引约 31 B/行，合计约 91 B/行。仅原始值约 **1.64 GB/天**，加 24 个派生点约 1.8 GB/天，未含 WAL。原文的 1.4 GB 约偏低 15%–30%，需要实测。 |

### 2.2 §13 未列出的缺陷

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| B1 | §7 的极端值规则 `x − N ≥ 2 abs(N )` 只适合"正常读数远离 0 且合法范围不跨倍数"的量。- N 很小时，正常波动即触发；- **N 为负时判据变为 x ≥ −N**，正常的符号反转（例如应变由压转拉）被判坏；- 对内外壁温差这类量，正常 15 ℃ 时，ΔT ≥ 45 ℃ 即判坏，而参考界面 `htsg_hmi.html` P4 恰把 40–80 ℃ 作为需要关注的瞬态区间。 | 在最需要监测的瞬态里把数据判坏，使相关计算失效；对应变、温差、压差这类双极性或零附近的量尤其明显。 |
| B2 | 取消整秒帧后，时间相关的计算（`derivative` 已在配置模式与开发配置中存在，见 `calculation.py:53-65`（历史文件已删除））失去定义：Δt 取自带抖动的接收时间，按变化上报的输入间隔不规则，"来一批算一次"对输入未变化的情况也无定义。 | 变化率结果的含义与误差不明确。 |
| B3 | §6"改为周期性 Read，一次请求就是一帧快照"不受 OPC UA 规范保障（见 A1）。 | 作为补救手段写入设计会造成错误预期。 |

### 3.2 Hybrid 的缺陷

| 编号 | 严重度 | 问题 | 建议修补 |
| --- | --- | --- | --- |
| H1 | **高（静默）** | 继承 §5 的"未通知即未变化"假设，没有通知缺口与陈旧检测。- 会话内通知丢失时，asyncua 不补；- 默认保活计数 2700 使断连判定与库自带的陈旧判定都失效。 | 明确请求较小的 `MaxKeepAliveCount`，使保活间隔加裕量小于看门狗，并核对服务器修订值；跟踪通知序号，出现缺口先 Republish，补不回则对该订阅执行一次 Read（maxAge=0）重同步；重同步完成前，受影响测点标为不确定。 |
| H2 | **高（静默）** | 只存变化值加"有效区间"后，进程崩溃或断电时**区间终点没有持久记录**，历史会把最后一个值一直延续到下次启动。原方案的保活重写正是为此存在，hybrid 取消它却没有给出替代。 | 每个源周期性持久化一条"存活至"水位（例如 10–60 s 一次，每源一行，远少于逐点重写）；启动时在最后水位处写入"中断"记录。这正是 PI 的停机事件做法，见 §5。区间终点的不确定度等于水位周期。 |
| H3 | 中 | 原始值立即推送、计算异步完成，会使同一画面出现"新温度配旧应力"。P4 这种页面正好需要相关量一致。另外"迟到结果不得覆盖较新状态"的规则引入了额外的状态复杂度。 | 现有算子都是微秒级：在状态所有者内同步计算，把同一批次的原始值与派生值放进**同一条推送消息**。重模型异步与待完成扩展已按用户硬边界取消。 |
| H4 | 中 | 没有定义时间相关计算（B2）。 | 明确规则：用同一源相邻两批的接收时间或源序号计算 Δt，并设最小 Δt 与抖动说明；或在新架构中暂不支持 `derivative`。 |
| H5 | 中（视配置） | 极端值规则沿用 §7（B1）。 | 改为按测点配置的**绝对物理上下限**（量程或工程极限），不用"正常值倍数"；未配置的不判。 |
| H6 | 中（视现场） | Modbus 输入无法单请求读取时，批次如何定义未说明。当前适配器是逐点请求。 | 把一轮轮询定义为一个批次：同轮共享批次号，每个值保留自身接收时间；同轮关系用于组织输入，不用于拒绝跨源组合。研究配置中现有算子都是单输入或同为 OPC UA 源，暂不受影响。 |
| H7 | 已裁定关闭 | 原提案曾要求跨源拒绝注册；2026-10-08 用户已撤销该保护与跨源扩展需求，此项不再列为待决问题。 | 本期不设计跨源正确性，也不因此阻断订阅或注册，不要求用户兜底；as-of、等待与重算预留废弃。 |

此外有一项已知限制，hybrid 如实接受，不计为缺陷：上游把同一组更新拆到相邻两次发布时出现的单拍新旧混合。只有接收时间戳时，这无法在后端消除。

## 4. 三方案对比汇总

| 维度 | 方案一（当前） | 方案二（§1–12） | 方案三（Hybrid） |
| --- | --- | --- | --- |
| 同批输入一致性 | 被整秒边界破坏（S2） | 有保障（单请求或单订阅时） | 有保障；Modbus 多请求情形待定义（H6） |
| 空值与丢值 | 0/2 样本即空（S1） | 无机械空值 | 无机械空值 |
| 展示延迟 | 约 1 s，最坏约 2 s（实测） | 宣称 100–150 ms，未实测 | 同左，需实测 |
| 断连判定 | 依赖连接检查 | 5 s 看门狗与保活计数冲突（A4） | 要求校验，但未定请求值（H1） |

结论：Hybrid 的形态与工业历史库和流处理的成熟做法一致。剩余缺口都有现成的对应模式，不需要另起架构。

| 问题 | 既有做法 | 对本项目的用法 |
| --- | --- | --- |
| 计算何时触发、输入先后到达 | AVEVA PI 分析服务默认**任一输入变化即触发**；全局 `CalculationWaitTimeInSeconds`（默认 5 s）用于吸收迟到输入，代价是结果延迟；迟到数据可按分析单独开启**自动重算**。社区里有同时间戳输入只触发第一次、因而缺结果的反馈，推荐的两段式是"定时检查输入是否到齐"。 | Hybrid 的批次触发与 PI 默认一致。相关跨源等待与迟到重算建议已取消，仅保留为外部资料背景，不作为本期任务或预留。 |

## 9. H1–H7 已确认实施合同（2026-10-09 归并）

本节已覆盖原初稿及第11节中的重复合同。记录、参数和恢复细则统一执行第13节规定；本轮写定方案，整体终审与代码实施分别进行。

### 9.1 H1：显式保活协商、连续性与重同步

使用应用管理的 `Subscription` 子类及创建流程，在 `publish_callback` 入口识别完整通知批次、序号和代次，区分空保活与数据通知，处理序号回绕。避免经由会自动重算保活参数的创建路径；通过库的订阅创建/修改接口提交参数，并保存服务端最终返回值，不能只相信本地请求字段。应用统一负责订阅删除、看门狗和重连，关闭库的自动重连。时限及库内健康检查的统一管理按第13.2节执行，不再固定为5秒看门狗。回调不等待数据库 I/O；协议接收、应用接纳和持久化分别记录状态。失步按 C1 处理，不做 Republish，不添加补传缓存系统。

**C1：缺号后重建订阅，不做 Republish。** 缺号、通知溢出或应用入口丢失后立即标记数据待同步，停止使用受影响旧状态确认故障或产生有效派生结果；通知运行所有者执行重建。新订阅使用新连接/订阅代次，旧代次迟到回调不得更新状态。收到相关计算所需测点的初始值和质量后再恢复该计算，缺失测点继续未知。初值只建立恢复时的基线，不回填失步历史。保活维持通信有效性，不视为新观测。代价是承认历史缺口、恢复期间短暂不可用。

重建使用有界退避，稳定运行后才复位；具体时限及持续失步后的动作见第13.2节。

### 9.2 H2：运行、归档段、水位与恢复

使用运行 ID、源 ID、连接代次、归档段、批次序号区分生命周期；同一连接内的归档缺口也必须切断历史有效区间。启动登记运行，正常停止在已接纳记录处理完后登记结束；重启发现未结束运行时，只承认已有持久化证据，不推测精确崩溃时间。水位目标每 10 s 提交一次，覆盖同源此前已持久化的完整提交组及状态，不能跨越未处理丢失。水位与依赖记录经过同一有序提交路径；同队列只是必要条件，还须保证事务完整提交后才更新水位。采用 C2 后新段可以推进，旧缺口永久保留。定时任务自身运行不能证明源仍有效，水位须有对应的有效通信和有序提交证据；没有水位时只保留实存点，不推断其后持续有效。10秒是提交目标周期，不确定尾段以实际持久化水位为准；阻塞期间没有固定上限。

**C2：先记录缺口，再重申当前状态，开启新的归档有效段。** 适用于“应用仍掌握可靠当前状态，但归档丢失”的情况；若采集入口本身失步，先按 C1 恢复，不能用旧缓存冒充可靠基线。为保持简单，归档恢复以受影响数据源整体为单位，无须实现逐点恢复调度。状态所有者在确定批次边界截取当前状态，保留原观测时间与值版本，另记重申时间及 `STATE_ASSERTION` 来源。重申只从该边界向后有效，不算新采样，不触发 change，不补算缺口中的故障。缺口、状态基线、新段及首个水位必须作为完整恢复单元提交；成功前不宣告历史恢复。恢复期间后续批次有界排队，再次溢出则重新截取基线，不能无界缓存。恢复记录也写不下时保留待恢复状态，历史继续显示未知。

**C3：应急路由同样接收原始与派生数据。** 原始、派生、必要状态和关联故障记录具有同一提交组身份；组内不得分别发往不同路由后仍标为完整。所有路由采用一致的记录语义与稳定 ID，重试不得产生重复历史。容量不足时整组拒写并进入 C2；取消应急路由主动丢弃派生结果的旧分支。统一水位减少了两套覆盖规则，但不等于保证应急容量无限或崩溃只丢一批。

C2基线同时覆盖该源派生结果。已生成但未提交的故障记录另在内存中有界保留，上限1000条，成功提交后移除；恢复时保留原确认时刻、依据值和稳定ID重交，不补算故障。满1000条后保留既有记录，拒绝新增缓冲记录并累计故障历史缺口；进程退出仍可能丢失内存记录，完整规则见第13.3节。

历史保持值的终点取下一次变化、连接有效期结束、归档缺口开始及该段已确认水位中的最早者；无效质量变化也终止此前有效值。重申值从重申边界生效，不能按其较早的原观测时间回填缺口。禁止插值、跨段取最近值和跨进程沿用单调钟。UTC 墙钟标记接收时间，单调钟计算持续时间，序号确定处理顺序；墙钟回拨产生重叠时间时保留段身份，不把不连续历史拼成唯一连续曲线。

### 9.3 H3：轻量同步计算与提交组

所有者内按依赖顺序处理当前轻量算子，一个逻辑输入批次产生一次一致状态更新，再交给推送与归档；保留输入版本依据和计算/配置版本，普通代数派生记录批次引用，8路strain_change另记录前一计划轮次依据，具体字段及还原规则见第13.1节，避免将批次外的旧值误认为同批输入。Modbus 按本轮输入，OPC UA 按订阅批次及连续有效缓存计算；两者都不宣称设备同步采样。当前 208 路输入、209 路派生量继续作为满量验证规模。采集目标 1 Hz；采用第10.5节的批次驱动推送与最多 100 ms 合并规则，不恢复机械整秒分窗。同批更新、计算和成组交付之间不await、不访问数据库；原始值及对应派生结果按完整发布组推送，前端整组应用，合并和慢客户端处理不得拆出新输入配旧结果。重模型及相关占位取消。

### 9.4 H4：应变变化与取消变化率

`strain_change = 本轮应变 − 紧邻上一轮应变`，仅在同一连接段、计划节拍编号连续的两轮该点均成功有效时产生，不除以时间。任一轮该点失败、极值无效、连接中断或计划节拍被跳过即清除其基线，恢复首轮只建立基线；禁止跳过失败轮后把跨多轮之差冒充相邻轮变化。其他测点的独立失败不必清除该点基线。移除 derivative 和 `demo_temperature_rate`，不增加新时间算子。

### 9.5 H5：极值、协议状态与普通故障

极值仍按[默认极值阈值](../默认极值阈值.md)识别不可用工程值，严格超界才触发，等于边界不触发，保留原值，不把 extreme 阈值作为普通故障阈值。普通故障按[默认越限阈值与回差](../默认越限阈值与回差.md)的 304 路执行：192 路温度、8 路过程量、96 路温差、8 路应变；不对 Bridge、应变变化或热应力代理重复设故障。

严格超过普通边界才开始计时，有效且连续越限满 5 s 确认；待确认阶段回到边界内即清零，确认后按回差复归。回差须支持上下限分别配置，例如给水温度上下方向默认值不同，不能用单个数值覆盖。复归边界为高侧 `value <= high - hysteresis_high`、低侧 `value >= low + hysteresis_low`；进入相反方向越限时重新计时。每秒由单调钟推进，先处理通信失效，再推进故障计时。无效/待同步取消待确认计时，但不将已确认故障自动复归。

**通信连续有效时，不变的越限值必须能够满 5 s 确认。** 不以“距上次值变化超过 1.5 s”判断连，也不识别死点/跳变。`freeze` 与 `bad/disconnect` 分开处理：冻结正常值不会越限，冻结越限值仍应确认。故障记录分开保存确认时刻、判定依据值的原观测时间与版本，不能伪造“第5秒新样本”。

协议状态采用 A：只有 Good 且通过类型、极值、来源有效性及完整性检查的值参与计算与故障确认。Bad、Uncertain 的原始载荷与完整状态码原样保留并标注，不因非 Good 擅自置空；协议本身无值时保留缺失，不补零。Good 不覆盖 Overflow 或待同步状态。使用上游状态不等于新增设备坏点诊断。

### 9.6 H6：Modbus 逻辑轮次

当前 8 路 Bridge 对应连续 16 个寄存器，在设备允许范围内合并为一次读取；每轮分配 poll_id；多请求时每个响应保留response_id及实际接收墙钟/单调时间，记录整轮起止和接收跨度，不将各响应改成同一时间。多请求场景只用本轮成功且有效的必要输入，不借上一轮补齐。轮次不重叠，不补发积压轮次；超时记录本轮失败；普通单次超时保留仍存活的连接，连续3轮超时或连接级错误触发重连，具体流程见第13.2节。通信成功与工程值有效分开，极端值不能被计为网络断连。删除迟到响应按原 poll_id 留档的承诺，不修改第三方库去截获迟到数据，也不将事务号不符必然导致下一轮失败写入合同。

1. **先确定记录与配置契约。** 定义紧凑类型化记录、稳定 ID、提交组、运行/连接/归档段及阈值回差字段；现场投运使用新库；旧开发库、研究库原样保留，不进入新回溯页，不增加旧格式兼容读取或迁移任务。
2. **完成批次入口和同步状态处理。** 落实 H1/H3/H4/H6，取消帧依赖，验证整秒边界不会拆错同轮计算、失败轮不被旧值补齐、旧代次回调无法覆盖新状态。

### 13.1 输入版本记录方案

普通代数派生采用批次引用，8路 `strain_change` 额外记录前一计划轮次依据。OPC UA与Modbus按各自批次语义还原，字段和处理顺序如下。

1. 派生结果定位到运行ID、源ID、连接/订阅代次、归档段、批次序号和公式/配置版本；版本必须能查到实际配置。相关原始、派生和质量状态记录按完整提交组持久化；自动清理保持暂停，不先删除还原依据。
2. OPC UA代数计算按同一有效段内、截至触发批次的有效状态还原；同批同点多通知共用该批实收时间，记录批内序号以保留顺序，明确批末状态用于本批代数计算。质量改变、无值、无效和失步均不能因数值未变而省略。
3. Modbus只使用本轮成功有效输入；缺失即不可用，禁止套用“最近一条”借到前轮。记录计划节拍编号及轮次成功/失败依据。
4. `strain_change` 记录当前与前一计划轮次的依据，两个编号必须连续且该点均有效。首次恢复只建基线，失败或跳拍后不跨轮求差。
5. C2状态重申分别保存原观测身份及新归档段中的生效边界，不能按旧时间/批次回填缺口。重申时已有的派生值可以作为恢复状态留存；若其原始计算依据已在缺口中丢失，明确标记依据不完整，不能宣称恢复了原计算过程。故障重交同样不能消除历史缺口。
6. 允许按上述记录核验同源结果，但不增加自动历史重算功能，不因跨源组合拒绝配置。存储节省量仍为估算，须计入索引、配置及状态记录实测，不能以旧0.2 GB/天估算保证总成本。

**实施验收：** OPC UA不同通知的输入、同批同点多通知、Modbus缺失轮、跳拍、C2重申、同代次恢复重申和质量单独改变均可定位实际依据或明确显示依据缺失；不得默默借用其他轮次或跨段值。

### 13.2 通信、运行时限与恢复

数据有效性与健康告警分离；确认故障仍固定持续5秒。保活仅证明通信活动，不能当成新采样；不设置按“距上次值变化”计时的逐点过期。下表为本期默认配置，服务端修订后须重新核对约束，不能把请求值当作生效值。

| 参数 | 默认值与执行规则 |
| --- | --- |
| 采集周期 | 1秒，已定 |
| Modbus连接/请求超时 | 各0.8秒；轮内重试0。分别限制一次操作，不保证整轮不跳拍 |
| Modbus单轮失败 | 该轮受影响输入不可用、清除对应change基线并取消待确认计时；单次超时不直接生成断连告警 |
| Modbus主动重连 | 普通超时连续3轮后重连；连接被拒、重置、关闭则立即进入重连流程。单次超时保留仍存活的连接 |
| Modbus断连告警 | 连续10秒无有效协议通信响应；有响应但工程量越限/极端或请求返回协议异常，与无响应分开标注，不能冒充网络断连 |
| OPC UA发布/采样周期 | 请求各1秒；核对实际修订值 |
| OPC UA测点队列 | 请求10条/点（按1秒采样，6秒重建阈值内每点至多约6个值，留有余量）；核对实际修订值，Overflow按失步处理。被修订为1时照常运行，健康状态标注“覆盖不可检测”，不判为不兼容 |
| OPC UA保活计数 | 请求2 |
| OPC UA数据有效期 | 最近一次当前订阅的有效发布响应后3秒；数据或保活均可证明活动，错误响应不冒充有效证据。到期只判数据失效，不触发重建 |
| OPC UA断连告警 | 连续6秒无有效发布响应；与数据待同步状态分开。同时是静默触发C1重建的阈值 |
| OPC UA订阅寿命/会话超时 | 请求寿命计数60、会话超时60秒；保存实际修订值，不承诺崩溃后一分钟内固定回收 |

| 持续失步 | 连续5次进入持续失步健康状态，继续按30秒间隔恢复；无需人工解锁，稳定60秒后清零 |

**约束及动作：**

- 0.8秒小于1秒只给单次请求留出余量。连接、多请求、解码及调度都计入整轮；跳拍按第9.4节处理，不补发积压轮次。撤销“约4.9秒必然恢复”“10秒等于两次重连失败”等时间线保证。
- 协商后的正常保活静默间隔加调度/传输裕量须小于数据有效期；告警阈值大于数据有效期，不少于正常静默间隔的3倍；寿命计数至少为保活计数的3倍。前端提示阈值大于两次心跳间隔。现场不满足时报告实际参数并按部署配置调整参数并重新校验，不能静默套用旧值。
- OPC UA超过3秒有效期只判数据失效：切断当前有效段、取消待确认计时，缓存保留但不参与计算，不触发重建。C1重建只由确定证据触发：缺号、Overflow、应用入口丢失、订阅或会话错误、明确连接断开，或连续静默达到6秒断连告警阈值；确定证据出现即重建，不必等待3秒。3–6秒内同一订阅恢复发布、序号连续且无Overflow时不重建，在同一代次内开新有效段：以保留的缓存（含该源派生结果）建立新段基线，即状态重申，保留原观测身份、数值和质量；再按序应用恢复批次，更新相关派生结果。新段、基线、恢复批次及更新后的派生结果按C2组成同一个恢复提交组，不得先单独提交或发布基线，以免旧缓存被短暂认证为新段当前值；实时状态在批次处理完成后整体发布，实时处理不等待数据库，历史水位在完整提交成功后推进。状态重申本身不启动故障计时；恢复批次同样按批内序号更新故障状态，待确认计时从处理后的最终有效状态重新开始；失效区间保留，不回填。重建时只有新代次所需初值和质量齐备后才恢复相关计算；迟到的旧响应不能恢复旧缓存，也不回填失效区间。重连尝试不重置“距最后有效通信”的告警计时。
- 3秒有效期只能缩短尚未发现的中断窗口，不能保证完全排除断连检测前的故障确认。例如越限已持续4.9秒时中断，仍可能在检测前达到5秒；这是有限观测条件下的已知限制。
- 队列为1时中间通知可能被覆盖且没有Overflow标记；发布序号连续不能证明监控项无丢值。改用小型有界队列并检查Overflow；服务端仍修订为1时照常运行并标注“覆盖不可检测”。同批同点多通知须按批内序号用于故障状态更新，不能先合并成最后值而吞掉恢复正常的中间值。此规则不承诺所有现场采样均被观察到。
- 应用统一管理订阅代次、重建和退避。asyncua 关闭 `auto_reconnect` 后，`connect()` 仍会启动连接监督任务（每隔 `watchdog_intervall` 读一次 `server_state`）和陈旧订阅任务（可自行 `recreate()`）；调大 `watchdog_intervall` 只是推迟检查，不是停用。确定做法：在项目适配层集中定义客户端子类，覆盖 `_connection_supervisor()` 与 `_stale_watchdog_loop()`，使这两个后台任务直接结束；保留正常 Publish、安全通道续期和底层连接状态更新，由应用统一处理有效性、告警及恢复，并统一创建、删除及重建订阅。两处均属私有实现依赖，锁定 asyncua 2.0.1，升级时复核。停用连接监督后，库不再触发 `connection_lost_callback`，也不再向订阅发送 BadShutdown；应用须在每次节拍检查连接状态（`check_connection()`，即 `_wait_until_ready()` 的兼容别名，状态为 DISCONNECTED 或 DISCONNECTING 时抛出 ConnectionError），或直接读取底层状态，发现断开即按明确断连处理，不必等待 3 秒。该检查只反映本地传输状态，半开连接仍由 3 秒有效期与断连告警发现。
- 服务端修订的采样、发布、队列、保活、寿命及会话参数都须保留；订阅回收依赖寿命计数、Publish请求供应及服务端行为，不能直接换算为崩溃后的固定回收时限。

**实施验收：** 覆盖单次超时、连续失败、明确断连、调度跳拍、静止越限、3秒失效后同代次恢复（基线与恢复批次同组提交并整体发布、重新计时、不重建）、6秒静默重建、Overflow及同批短暂正常值、参数修订（含队列被修订为1）、连续失步退避，以及库内后台任务已停用：没有库内周期 Read 和自主 `recreate()`，底层断连仍被应用接收，正常 Publish 与安全通道续期继续工作。满200个OPC UA订阅点及8路Modbus联调，测量端到端延迟、队列峰值、维护阻塞与恢复时间。

协议依据：[队列与Overflow](https://reference.opcfoundation.org/specs/OPC-10000-4/5.13.1.5)、[会话协商](https://reference.opcfoundation.org/specs/OPC-10000-4/5.7.2.2)、[订阅参数](https://reference.opcfoundation.org/specs/OPC-10000-4/5.14.2.2)。本地证据：asyncua `client.py` 的 `connect`、`_stale_watchdog_loop`、`_wait_for_health_signal`；不把已有源码核验等同于现场验证。

### 13.3 故障缓冲满额处置
