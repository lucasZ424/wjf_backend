## 1. 结论与证据边界

当前适合先补测试准备和定向复现，再运行完整套件；不能宣称全量验收或最终交付通过。下列六项源码缺陷及一个段收尾边界均未修复。取消问题虽此前被单列排除在通信页开发之外，仍直接影响连续运行与正常停止，不能用分段测试通过替代它的处理。

证据分为三类，不混用：

- **上一轮只读源码/内存探针：** 六项缺陷及 `lost_seg` 边界的结论见第2节。内存探针不等于真实数据库、协议服务器或完整运行验收；本报告没有重跑这些探针。
- **上一轮测试事实：** `pytest tests/test_comm_log.py -q -p no:cacheprovider` 为45项通过；`pytest --collect-only -q -p no:cacheprovider` 收集632项，仅证明本地可收集。日志/失步/通信事实的组合运行未完成并中止，不能计为通过。
- **已有开发记录：** D44f记录两段合计631项通过，之后新增1项及局部复跑，形成632项本地用例；并非同一版本一次连续运行全部通过。D46/D47旧测量及D48旧烟测只支持其当时的候选版本。

模拟输入是否覆盖现行架构另见[模拟信号与当前架构适配审核](HTSG_V1_模拟信号与当前架构适配审核_v0.1.md)。本报告不调整模拟场景或参数。

## 2. 源码问题与最小验收

本节P1指影响连续运行、历史可信度或敏感信息处理的优先问题；P2指必须补齐的稳定性及有界性问题。优先级不是测试结果，所有条目状态均为**未修复**。

### Q01 / P1：Modbus取消可能被当作请求超时继续处理

**证据：** [modbus.py](../htsg/modbus.py)第155行捕获 `ModbusIOException` 并按超时继续；pymodbus会把读请求等待期间的取消转换为该异常。停止路径在[runtime.py](../htsg/runtime.py)第149、157行等待采集任务结束。既有审核已指出取消恰逢读请求时可能不退出，连续测试与正常停止会挂起；不是所有历史挂起都已证明由此导致。

**最小验证与建议验收：** 用受控等待的真实Modbus请求复现“读请求中取消”，同时覆盖两轮之间取消；确认任务在约定停止期限内结束、没有后续轮次，`Runtime.stop()`不无限等待。保留数据库未启动和其他挂起原因的独立诊断，不以终止pytest进程冒充正常收尾。本报告不实现取消修复。

### Q02 / P1：崩溃收尾使用全运行最晚证据，可能延长另一来源的历史

**证据：** [archive.py](../htsg/archive.py)第295–310行按整个run取最大证据，再以同一时刻封闭全部开放段；[history.py](../htsg/history.py)第181行的已闭段路径不再按该段水位截断。上一轮纯内存重现：某源观测1001、水位1002，段被标为 `EXIT_TRUNCATED=1010` 后，查询返回保持至1010。跨源或其他证据的较晚时刻不能证明该源持续有效。

**最小验证与建议验收：** 两个来源分别停在不同水位，模拟异常退出后用真实测试库执行收尾和查询；验证每源的保持终点不越过自身可证明边界。覆盖有水位、无水位及较晚其他状态记录，不只断言run已标记异常结束。

### Q03 / P1：RUN_END可能先于恢复期间待提交的数据入队

**证据：** [owner.py](../htsg/owner.py)第227行恢复期间暂存pending，第269行确认后释放；第906行直接提交 `RUN_END`。上一轮内存探针观察到提交顺序为恢复组order4、RUN_END order7、数据order5、SEG_END order6。数值编号不是数据库提交顺序，已登记正常结束不等于相关记录已按序完成。

**最小验证与建议验收：** 阻塞C2恢复提交确认，接纳后续数据后立即正常停止，再释放确认；核对提交和数据库实际顺序，最后的运行结束不得越过依赖记录。覆盖恢复失败、停止写入等待到期，不能把未落库尾部标为完整正常结束。

### Q04 / P1：超长带凭据URL可能绕过完整脱敏

**证据：** [commlog.py](../htsg/commlog.py)第58–63行先按4096字符限长，再执行URL等脱敏。上一轮用完全合成的 `opc.tcp://user:`、重复秘密占位串及尾部 `@localhost/` 探针，输出仍含秘密前缀；预截断移除了辨认userinfo所需的后半段。没有使用或记录真实凭据。

**最小验证与建议验收：** 覆盖userinfo跨4096边界、无空格长URL、带口令/令牌的异常及普通长文本，断言输出不含任何合成秘密片段，同时满足长度上限及截断标记。不能只验证512字符上限或短URL脱敏。

### Q05 / P2：部分请求超时仍可能被计为稳定通信并清零失步累计

**证据：** [owner.py](../htsg/owner.py)第734–737行仅按整轮outcome决定是否中断稳定区间；Modbus一轮可能同时有TIMEOUT与OK。上一轮构造61轮部分超时加成功应答，失步累计最终变为0，与“超时中断连续稳定区间”的既定语义不符。

**最小验证与建议验收：** 多请求轮持续一部分超时、一部分成功超过60秒，验证通信活动仍可记录，但稳定计时不能据此清零；随后连续完整成功60秒才清零。保留协议EXCEPTION与无响应的区别，不能直接把所有部分失败冒充整源断连。

### Q06 / P2：请求失败详情可未经限长进入业务入口队列

**证据：** [modbus.py](../htsg/modbus.py)第157行将原始 `str(error)` 放入 `RequestResult`，随批次进入[ingress.py](../htsg/ingress.py)；到[owner.py](../htsg/owner.py)第764行消费时才清理。诊断事件自身的入队限长没有覆盖该路径，因此队列条数有界不等于详情内存有界。

**最小验证与建议验收：** 生成超长合成错误详情并暂停owner消费，检查排队批次中的详情已经脱敏、有长度上限和截断标记；验证既有请求结果、协议码与整组语义保持。不要依赖消费后的日志长度证明入队内存已受约束。

### Q07 / P2：lost_seg不能覆盖所有丢失期间的段收尾

**证据与限定：** [owner.py](../htsg/owner.py)第525行失效时清除open_segment，而LOST阶段的SEG_END不能落库；第341行恢复组仅在open_segment为真时补结束。上一轮探针为101观测、102提交拒绝、105失效、105.5恢复，恢复单元只有GAP/SEG_START/WATERMARK，没有旧段SEG_END。旧段元数据可能仍开放；但缺口确实存在，**不能据此宣称查询已经直接跨缺口保持**。执行记录另列的其他lost_seg边界仍需逐项复现，不能都视为已证实。

**最小验证与建议验收：** 对上述序列在测试库核对旧段结束事实、缺口和新段；再分别复现丢失组本身含SEG_START、恢复再次被拒等边界。既要保证段元数据收尾，也要验证查询仍受缺口与水位限制，不删除缺口来“修复”状态。
