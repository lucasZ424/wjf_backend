## 3. 运行入口与切换

候选版本默认启动只走新链路（`htsg.cli run`），入口加载的模块中没有旧的帧、窗口、Profile、计算器或旧存储链路（`tests/test_runtime.py` 在干净解释器里核对）。**本次没有切换、停止或重新注册任何用户现行的服务或计划任务**；切换由部署人员按 README 执行：停止现行服务 → 换成本版本的代码与配置 → `run.ps1` 或重新注册任务计划。旧版建的库不会被读写（识别后拒绝），新版用新库启动。

**停止语义（Windows）：** Ctrl+C／Ctrl+Break 是正常停止（运行以 `NORMAL` 结束，uvicorn 之后会向自己重发该信号，进程退出码为 3，不是错误）；任务计划的“结束任务”等于硬杀，下次启动时未结束的运行按库内最晚证据收尾为 `ABNORMAL_EXIT`。部署要知道这一点，不要把后者当成故障。

## 4. 采集与订阅参数表（逐源逐订阅）

**Modbus：`mb_field`（本模拟 127.0.0.1:15020）。** 一个轮次读一次寄存器，每轮一个计划号；失败的轮次是失败的轮次，不用上一轮填补。

| 项 | 请求值（配置） | 实际 | 说明 |
| --- | --- | --- | --- |
| 周期 | 1 秒 | 1 秒（计划号连续证明连续轮次） | 迟到不补发，跳过的轮次在计划号上留下空缺 |
| 每轮请求 | — | 1 次，16 个寄存器（8 路 float32） | 单设备、连续地址 |
| 连接／请求超时，重试 | 0.8 秒／0.8 秒，0 次 | 同请求值 | 库不自行重连，应用决定 |
| 连续超时触发重连 | 3 次 | — | 单次超时不断连接 |
| 通信告警 | 10 秒 | — | 与“数据状态”分开显示 |

**OPC UA：`ua_field`（本模拟 `opc.tcp://127.0.0.1:…`，一个订阅，200 个监控项）。** 下表是烟测（`docs/evidence/d48`）里 `/api/health` 报告的服务器实际授予值。

| 参数 | 请求值 | 实际授予 | 备注 |
| --- | --- | --- | --- |
| 发布周期 | 1 秒 | 1.0 秒 | |
| 采样周期 | 1 秒 | 1.0 秒（200 项最小＝最大） | |
| 保活计数 | 1（测量与烟测所用）；库默认为 2 | 1 | 见下面的说明 |
| 寿命计数 | 60 | 60 | 不小于保活计数的 3 倍 |
| 测点队列 | 10 | 10（最小＝最大，200 项） | 队列大于 1：溢出可检测，按失步处理 |
| 会话超时 | 60 秒 | 60 秒 | |
| 队列能力 | — | `OVERFLOW_DETECTABLE` | 被服务端修订为 1 时变为“覆盖不可检测”，页面标出 |
| 约束违反 | — | 无 | 静默＋裕量 < 数据有效期、告警 > 有效期 等 4 项检查 |

**保活计数的说明：** 上表保留2026-10-13候选的实际历史配置。后续复核确认，未适配的asyncua 2.0.1测试服务器比协商值晚两个发布周期：请求2实际约4秒，请求1约3秒；旧说明的3秒／2秒量值不正确。2026-10-16的R06工作区已对项目自建的模拟服务器实例安装局部适配，使请求2／1分别约2秒／1秒，并撤销measure、smoke及正常测试入口的计数1绕行；生产客户端、第三方服务器和3秒有效期没有改变。新候选D46/D47/D48证据尚待刷新，**真实网关的保活行为仍必须现场核验**（见第5节）。

**覆盖限制（写进交付，不是缺陷）：** 发布序号连续只证明发布连续，不证明监控项没有丢值，除非队列大于 1 且溢出被检测；队列被修订为 1 时照常运行，但“覆盖不可检测”。订阅回收依赖寿命计数、Publish 请求供应和服务端行为，不能换算为崩溃后的固定回收时间。时间域是接收时间，不是现场同时采样；页面的共同时间轴只便于观察。

## 5. 尚需真实 Acheron、UA 网关和实际卷验证的项目

没有下列项目的证据；它们不能由模拟环境的结果替代。

1. **真实设备与点表：** Acheron 的 Modbus 地址、寄存器格式与字序、实际 8 路 Bridge 的量程与极值；现场 NodeId 与通道命名；GF 标定与温度补偿资料（本期按 GF=6 换算，不预留补偿）。
2. **真实 OPC UA 网关：** 实际修订的发布、采样、队列、保活、寿命与会话参数；保活是否晚于协商值；测点队列是否被修订为 1；断连后的订阅回收行为；证书与安全模式。
3. **实际卷与磁盘：** 主数据盘、移动盘、应急库各自所在的物理卷；移动盘独立卷校验；95 % 与 70 % 切换在真实磁盘空间下的行为（本期只有注入读数）；`emergency_reserve_bytes`（默认 100 GiB）在实际卷上的余量。
4. **一年容量：** 现场实际的变化速率（模拟的上界是每秒全变，一年约 10.5 TB，不通过；静止下界约 0.90 TB）；实际卷的可用空间与余量；WAL 与维护峰值在长时间运行里的表现。
5. **长稳与开机：** 现场启动、无人值守开机（PostgreSQL 自动启动、服务账号目录权限）、长时间运行下的内存趋势（本次 180 秒涨 11.3 MB，未证明持平）与长稳。
6. **多人使用：** 多个浏览器同时在线、慢客户端在真实网络上的表现（本期用本机回环与真实 WebSocket 验证了切断与恢复）。

- **通信·日志页的实现取值（2026-10-14，出处与理由见执行记录 D44a–D44f，请知悉）：** ① 订阅的首个有效响应本身也算“等待已开始”（`begin_waiting` 事件之外的兜底，超出条文）；② Modbus 每个请求的结果随批次交给 owner（不另发诊断事件），日志里单条事件分“失败信号”（重新同步、数据失效、告警、应用丢失，不切断同一段失败）与其他事件（结束失败聚合）两类，这是我对条文“其他非失败事件”的读法；③ `UaAcquirer` 另按配置的用户名/口令环境变量的实际值替换错误详情（超出条文，防库的报错带出口令）；④ `/api/health` 无条件带上日志与读数表，最坏每次约 350 KB，自检页每 5 秒也读它——要省可加只在通信页请求时才带的查询参数，由你定；⑤ 真实 pymodbus 在这台 Windows 上对无人监听的端口，默认配置下记的是“应用超时”而不是“库未提供原因”（库的超时先到时才返回 `False`），两种都如实区分；⑥ 设计侧文档（终版第 15 节、15.1 开头，方案头部与第 12 节，核验文件）仍写“通信页尚未实现”，我没有动，是否回写由你决定。
- **一年容量按终版口径不通过**（模拟满量约 10.5 TB/年，可用卷 1.33 TB），行宽约 800 字节/行是主因；终版里“3.3 GB/天”与满量实测相差约 8.7 倍。是否调整存储形式（如把重复的文本列与 JSON 依据改为引用）是设计取舍，没有在本期做。
- 100 毫秒合并等待的最大值在实测里到过 330 毫秒（事件循环偶发迟到 272 毫秒，原因未查明）；中位 102 毫秒，总延迟 p99 129 毫秒。
- 删除了 `config.simulator` 源与开发观测注入入口、`/api/current`、`/api/history`、事件类接口、旧的页内历史设置；`config` 里旧机制字段不再被接受。
- 实现取值：`limits.commit_queue` 默认 400 组取代 `ordinary_queue/event_queue/write_batch_records`（终版第 18.1 节说这些是“实现基线、按第 16 节验证”，新链路是单一有序队列）；`Negotiated.as_dict()` 增加了采样周期与队列的范围，供本表使用。
- 前端不做移动端布局（用户指示 2026-10-12）。
