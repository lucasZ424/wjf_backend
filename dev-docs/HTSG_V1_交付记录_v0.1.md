## 3. 运行入口与切换

候选版本默认启动只走新链路（`htsg.cli run`），入口加载的模块中没有旧的帧、窗口、Profile、计算器或旧存储链路（`tests/test_runtime.py` 在干净解释器里核对）。**本次没有切换、停止或重新注册任何用户现行的服务或计划任务**；切换由部署人员按 README 执行：停止现行服务 → 换成本版本的代码与配置 → `run.ps1`，或在现场用 `deploy_databases.py register` 重新注册任务。旧版建的库不会被读写（识别后拒绝），新版用新库启动；新库用 `bootstrap_db.py new --name htsg_<x>` 另建。

**看守程序（`scripts/supervise.py`）：** 任务 `HTSG-Backend` 以 SYSTEM 身份在开机时、并每5分钟运行一次（已在运行就不重复）。它把没在运行的库服务拉起来，等主库能连上再启动后端（最多3分钟）；后端无论因何结束都再启动，连续很快结束时间隔从5秒加倍到60秒，运行满10分钟后复位。启动后120秒内 `/live` 不应答，就按停止同样的方式停掉（先 Ctrl+Break，宽限期60秒后强制结束），再按退避重启；就绪后不再探测。`.local/STOP` 存在时以正常方式停止后端并退出、不再启动。完整控制链已通过缩短启动期限和退出宽限期的真实进程用例验证；生产设置分别为120秒和60秒，退避决策也已验证。它起的是虚拟环境的 `python.exe` 启动器，强制结束启动器时真正的解释器随之结束（本机验证）。任务注册本机未执行，见第5节。详见[修复轮01](HTSG_V1_修复轮01_存储路径失效与无人值守_v0.1.md)、[修复轮10](HTSG_V1_修复轮10_查询边界与启动依赖_v0.1.md)。

**停止语义（Windows）：** Ctrl+C／Ctrl+Break是正常停止（uvicorn之后会向自己重发该信号，进程退出码为3，不是错误）。正常停止不等于“运行以NORMAL结束”：停机先等每个来源的终结组（缺口与段收尾）落库，最多约8秒，之后才提交运行结束记录；只有运行结束记录被确认提交才登记`NORMAL`。队列满、写入被拒、写入卡住或运行结束的提交结果不明时**不登记**，健康输出里`shutdown_incomplete`为真，并给出`run_end_status`（`NOT_QUEUED／UNCONFIRMED／COMMITTED／REFUSED`）、`failed_sources`和`unsettled_queue_items`；这些不得解释为“零数据丢失”，终结组不带内存中的故障缓冲（细则约定M）。停机开始时通知维护线程停止，在归档收尾预算的剩余时间内有限等待（最多5秒），结果记在健康输出的`maintenance_stopped`；未确认退出不视为已经停止。未完成删除保留“删除中”状态；下次启动时，自动清理启用则恢复清理过程并继续至停止线，关闭时只完成已标记范围。任务计划的“结束任务”等于硬杀。两种未登记`NORMAL`的运行，下次启动都按各段已持久化的水位收尾为`ABNORMAL_EXIT`（没有水位的段取段起点；水位之后的观测仍在库里、照常显示，只是不再被保持到更后面；收尾只读小表，耗时不随崩溃运行的大小增长，2026-10-23）——部署要知道这一点，不要把它当成故障。

## 4. 采集与订阅参数表（逐源逐订阅）

**Modbus：`mb_field`（本模拟 127.0.0.1:15020）。** 一个轮次读一次寄存器，每轮一个计划号；失败的轮次是失败的轮次，不用上一轮填补。

| 项 | 请求值（配置） | 实际 | 说明 |
| --- | --- | --- | --- |
| 周期 | 1 秒 | 1 秒（计划号连续证明连续轮次） | 迟到不补发，跳过的轮次在计划号上留下空缺 |
| 每轮请求 | — | 1 次，16 个寄存器（8 路 float32） | 单设备、连续地址 |
| 连接／请求超时，重试 | 0.8 秒／0.8 秒，0 次 | 同请求值 | 库不自行重连，应用决定 |
| 连续超时触发重连 | 3 次 | — | 单次超时不断连接 |
| 通信告警 | 10 秒 | — | 与“数据状态”分开显示 |

**OPC UA：`ua_field`（本模拟 `opc.tcp://127.0.0.1:…`，一个订阅，200 个监控项）。** 下表是烟测（`docs/evidence/d48`）里 `/api/health` 报告的服务器实际授予值。

| 参数 | 请求值 | 实际授予 | 备注 |
| --- | --- | --- | --- |
| 发布周期 | 1 秒 | 1.0 秒 | |
| 采样周期 | 1 秒 | 1.0 秒（200 项最小＝最大） | |
| 保活计数 | 1（测量与烟测所用）；库默认为 2 | 1 | 见下面的说明 |
| 寿命计数 | 60 | 60 | 不小于保活计数的 3 倍 |
| 测点队列 | 10 | 10（最小＝最大，200 项） | 队列大于 1：溢出可检测，按失步处理 |
| 会话超时 | 60 秒 | 60 秒 | |
| 队列能力 | — | `OVERFLOW_DETECTABLE` | 被服务端修订为 1 时变为“覆盖不可检测”，页面标出 |
| 约束违反 | — | 无 | 静默＋裕量 < 数据有效期、告警 > 有效期 等 4 项检查 |

**保活计数的说明：** 上表保留2026-10-13候选的实际历史配置。后续复核确认，未适配的asyncua 2.0.1测试服务器比协商值晚两个发布周期：请求2实际约4秒，请求1约3秒；旧说明的3秒／2秒量值不正确。2026-10-16的R06工作区已对项目自建的模拟服务器实例安装局部适配，使请求2／1分别约2秒／1秒，并撤销measure、smoke及正常测试入口的计数1绕行；生产客户端、第三方服务器和3秒有效期没有改变。后续相关修复按记录刷新 G3，最近一次是候选`abdd252`（本地`docs/evidence/g3-20261030-r10/`）；**真实网关的保活行为仍必须现场核验**（见第5节）。

**覆盖限制（写进交付，不是缺陷）：** 发布序号连续只证明发布连续，不证明监控项没有丢值，除非队列大于 1 且溢出被检测；队列被修订为 1 时照常运行，但“覆盖不可检测”。订阅回收依赖寿命计数、Publish 请求供应和服务端行为，不能换算为崩溃后的固定回收时间。时间域是接收时间，不是现场同时采样；页面的共同时间轴只便于观察。

## 5. 尚需真实 Acheron、UA 网关和实际卷验证的项目

没有下列项目的证据；它们不能由模拟环境的结果替代。

1. **真实设备与点表：** Acheron 的 Modbus 地址、寄存器格式与字序、实际 8 路 Bridge 的量程与极值；现场 NodeId 与通道命名；GF 标定与温度补偿资料（本期按 GF=6 换算，不预留补偿）。
2. **真实 OPC UA 网关：** 实际修订的发布、采样、队列、保活、寿命与会话参数；保活是否晚于协商值；测点队列是否被修订为 1；断连后的订阅回收行为；证书与安全模式。
3. **实际卷与磁盘：** 主数据盘与应急库各自所在的物理卷（移动库已移除）；删除启动线90%、停止线80%与主库95%转应急，在真实磁盘空间下的行为（本期只有注入读数）；`emergency_reserve_bytes`（默认 100 GiB）在实际卷上的余量；应急库能撑多久取决于系统盘实际空闲，现场还没有这个数据。
4. **容量与删除周期：** 终版[第13.5节](HTSG_V1_终版设计_v1.0.md#storage-routing)已不做一年验收。按现场 2 TB 数据盘、启动线90%、停止线80%、保底14个桶，用模拟现场的实测增长率推算：满量（208路每秒全变）每天约29.3 GB，约6.8天删一次，删除后保留约55天、下次清理前约61天；40路 OPC UA 每秒变化（其余160路不变，Modbus 8路照常；这次测量不属于候选 G3）每天约7.5 GB，约26.5天删一次，删除后保留约212天、下次清理前约239天。均为模拟负载和指定容量、阈值下的估算，不保证最低保留天数；实际其他文件占用及长期增长会改变结果。实际删除周期与保留时长、WAL 与维护峰值、R03a 大库收尾耗时与冷盘读取，须现场实测。
5. **长稳与开机：** 现场启动、无人值守开机（PostgreSQL 自动启动、服务账号目录权限）、`register`（开机任务计划）与看守程序在现场电脑上的实际行为、BIOS“来电自动开机”、现场电脑（i5-14400）上的 scrypt 耗时（兜底认证每次请求最多两次，本机单次约34毫秒）、长时间运行下的内存趋势（本次 180 秒涨 11.3 MB，未证明持平）与长稳。
6. **多人使用：** 多个浏览器同时在线、各自每秒读取一次当前状态；慢网络上的表现（本期在用例里验证了读取失败或挂起不影响采集与归档）。

  - 缺桶长期等待：主库一直补不上某一组的桶时，该组留在队首，不超时丢组、不自动换库；补桶持续失败时历史归档可能长时间中断，采集与实时显示照常。四条接受条件都有测试证明，自检页看得到等待提示。
- **验证范围与其他限制：**
  - “满3秒”的中断边界没有行为测试：检查每500毫秒一次，时刻对不齐，是读代码静态核对的。
  - 没有保留边界基线的旧数据（测试造数或升级前的桶）：起点值最坏可回查至段起点，开销可能接近改前；找到足够新的基线即提前停止，不是每次都退到段首。480个桶时23毫秒的规模测量不代表这种情况。
  - 历史查询连接：每个工作线程对每个库保留一条历史查询连接，在有界线程池内复用；按现场约20个池线程，每个实例约23条连接，部署设 `max_connections=60`（[终版第17.4节](HTSG_V1_终版设计_v1.0.md)）。
  - 启动时数据库不可读：任一绑定库读不了时，跳过上次未结束运行的整体收尾，运行中不自动补做，数据库恢复后在下一次启动补做；看守程序先等主库只能部分缓解。本次模拟交付保留这一点，现场无人值守验收不能宣称已覆盖。
