## 1. 问题与用户裁定

核实（读代码）：

1. **单次回放没有通道数上限（审核 B）：** 回放接口只按每通道1万行限量。历史页“查看通道”是全部417个通道的多选，查询时把所有选中的通道放进同一个请求，切换图表通道又会把它们全部重查。最坏一次 417 × 1万行（每个库），这些行在驱动缓冲、逐行数据和返回的 JSON 里至少各有一份；允许两个查询同时进行。内存耗尽时，任何一个核心任务申请内存失败都会让进程退出。
2. **与用户本意不符：** 用户说明，当初加入历史查询设计时的本意是每次只查当前查看的通道；终版第14节没有写明，实现成了多选后一次查全部。点故障时现在只选故障通道本身，窗口长度沿用上次的设置（页面初始值300秒）。导出只用已显示的结果，不另行查询。

用户裁定（2026-10-26／27）：

- 不做按故障类型变化的动态前端：用一个固定模板，通道数取各类故障判断需求的并集，不按单个故障计。
- 现场没有拓扑图：不做邻点；“本段应变”和“应变对应的那一对”同样只来自模拟点表的编号规则，也不用。模板只用配置里写明的计算关系：**8个工况量**（没有被任何派生量用作输入的输入量）＋**故障的计算链**（故障通道的输入、以它为输入的派生量及这些派生量的其余输入；热应力峰值这类多输入的汇总量不展开）。按现行点表对304路有越限判定的通道逐条验算：壁温、温差12个，应变11个，过程量8个，最多12个。
- **单次回放最多12个通道。**
- **点故障时窗口长度重置为默认值。** 默认值按实测定：12个通道前后各30分钟有余量取3600秒，否则取1800秒；前后各1小时在工程上常用，手动可选。

方案（用户 2026-10-27 同意）：后端拒绝超过12个通道的回放（422）；按配置算出每个越限通道的模板，经 `/api/ui-config` 交给页面；点故障时按模板一次查询；手动查询最多选12个；页面布局（汇总表、单个焦点图表、记录表、导出）不变。

## 2. 实测

脚本与结果在本地 `docs/evidence/r03-replay-20261027/`（`replay_measure.py`、`replay-24h.jsonl`，不入库），2026-10-27 11:25–11:40。

- **做法：** 在开发实例上建一次性库，按归档实际的写入顺序（逐秒、所有通道交错）灌入24小时满量数据：研究配置的208路输入和209路派生量每秒都变化，观测17,971,200行、派生18,057,600行，两表连同索引约6.8 GB和6.4 GB，测完删除。查询走真实的 Web 应用（`GET /api/replay`，生产超时：每条语句3秒），模板为壁温故障 `temp_inner_09` 的12个通道，中心取数据中点；每种窗口在一个新进程里连测3次，记录耗时、行数、响应大小和进程的峰值工作集。
- **结果：**

  | 窗口 | 耗时 | 行数 | 响应大小 | 进程峰值内存 |
  | --- | --- | --- | --- | --- |
  | 前后各15分钟 | 0.55–0.66秒 | 21,612 | 7.0 MB | 113–149 MB |
  | 前后各30分钟 | 1.02–1.19秒 | 43,212 | 14.0 MB | 149–252 MB |
  | 前后各60分钟 | 2.37–3.01秒 | 86,412 | 27.9 MB | 241–457 MB |
  | 前后各60分钟，两个同时 | 4.27–4.63秒 | 各86,412 | 各27.9 MB | 372–732 MB |

  三种窗口都没有被每通道1万行的上限截断，都没有部分可用。3秒是单条语句的超时：观测表窗口语句（10路输入）在前后各15、30、60分钟时分别用52、107、471毫秒，从 PostgreSQL 缓存之外读入约26、80、570 MB；整个请求的其余时间主要花在拼装结果和生成 JSON 上。进程峰值内存是该进程至今的最大值，后两次包含上一次结果尚未释放的部分，偏保守。
- **判定（用户 2026-10-27 的规则）：** 前后各30分钟单次约1秒，窗口语句约0.1秒，离3秒超时有充足余量，**默认窗口长度定为3600秒**。前后各60分钟也能在超时之内完成，可手动选用。
- **局限（未测）：** 开发实例 `shared_buffers` 为32 MB（现场256 MB）、`work_mem` 2 MB（现场4 MB）、`temp_file_limit` 32 MB（现场不限），偏保守。刚灌完的库可能仍在 Windows 文件缓存里，真正的冷盘读取没有测；按读入量估算，前后各60分钟在普通固态盘上约多1秒，在机械盘上可能超过3秒——那时这次查询失败（页面显示读取失败或部分可用），不会崩溃或卡住。现场磁盘类型未知。数据为每秒都变化的最坏密度；一年数据量的库索引更深，但单次查询的主要开销是窗口内的数据页，数量与库的总量关系不大。

## 3. 改动

- **`htsg/history.py`（候选摘要随之改变）：**
  - `CHANNEL_LIMIT = 12`：单次回放最多12个通道。
  - `DEFAULT_WINDOW_SECONDS = 3600`：点故障时带出的窗口长度（前后各30分钟），按第2节实测定。
  - `replay_template(config, channel)`：依次是故障本身、它自己的输入（按声明顺序）、计算链的其余部分和工况量（按配置顺序），最多12个。只用配置里派生量的输入关系，不用拓扑；输入超过2个的汇总量（热应力峰值）不展开。
- **`htsg/history_api.py`：** `/api/replay` 超过12个通道返回 422。
- **`htsg/web.py`：** `/api/ui-config` 增加 `replay`：上限、默认窗口长度、每个有越限判定的通道的模板；启动时由配置算出，运行中不变。
- **`htsg/static/app.js`（页面摘要随之改变）：**
  - 点故障：填中心时间，把窗口长度重置为默认值，按模板选通道并一次查询，图表默认显示故障通道。
  - 手动选择最多12个，超出时这次选择不采用，并说明原因。
  - 窗口初始值和“清空设置”后的值改为默认值（原为页面里写死的300秒）；说明文字相应改写。
- **`README.md`：** 接口表注明单次最多12个通道。
- **未改：** 每通道10000行上限、跨库合并、截断标记、导出规则；采集、归档、启动和重启路径。
