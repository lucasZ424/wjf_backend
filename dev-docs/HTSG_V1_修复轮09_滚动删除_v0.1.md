## 1. 用户裁定

- 拆分与顺序（2026-10-29）：09a 配置→结构6 建库入口→09b 分区与写入→09c 维护线程→09d 标桶、换桶与路由→09e 保留边界基线→09f 删除→09g 查询→09h 自检与报警→09i 工具→09j 验收。
- 五条调整：`cleanup_enabled=false` 只不启动新的删除，分桶、准备桶、基线、查询标注照常，已标为删除中的范围照样删完；维护线程只做数据库工作，路由决定留在写入路径，不持跨线程锁等库；查询分开“已删除／正在淘汰”与“可能不完整”；结构6 测试库的建库入口提前；验收顺序为各步针对性验证→G2→提交候选→在该候选上跑 G3。
- 首次启动：已有可写的桶时直接启动；新库没有桶时整个准备过程最多等5秒，超时照常采集，同一个后台任务继续准备；空库首次初始化与编号文件丢失的既有部署分开。
- 累计运行时长：约每60秒保存一次累计值；异常退出时未确认保存的不计；维护延迟或保存失败时可能少算更多；封桶前须确认满12小时的证据已保存，否则继续用当前桶。
- 桶机制 D1–D8（终版未写到的细节，用户“按草稿实施”）：
  - D1 桶状态：维护线程建“待用”；写入线程在写某组的同一事务里把该组的桶改为“当前”、本库更旧的“当前”或从未用过的“待用”桶改为“已封闭”；删除线程只改“删除中”“已删”。
  - D2 某库缺某桶：重新上线后由维护线程补建；写入时主库缺这一组的桶，确认未写入后整组改写应急库（`NO_BUCKET`），应急库也缺则拒写记缺口。**“改写应急库”一句已被下面评审第4条的裁定取代。**
  - D3 累计运行时长与桶号一起存在本机编号文件，写临时文件、强制写盘、原子替换。
  - D4 维护线程把各库可用的桶号作为只读快照整体交回，状态所有者只读快照。
  - D5 提交组带桶号；写入、“已写过”、结果不确定的核验、回退都按组号加桶号，桶号不变。
  - D6 分区表主键为记录号加桶号，记录号在前。
  - D7 首次启动见上。
  - D8 维护线程独占一条线程、每库一条专用连接（等锁1秒、单条语句60秒），准备与续删交替；`router.maintain()` 留在写入线程。
- `cleanup_enabled` 作为滚动删除的总开关（审核第01-2条，与终版第18.1节一致）。
- 评审五条（2026-10-29）：五条都修；第4条“重试沿用原库”维持[终版](HTSG_V1_终版设计_v1.0.md)第13.5节：主库模式下主库缺这一组的桶时在主库等待，不转应急，与 D2 字面冲突处以终版为准。
- Modbus 测试竞态改成确定的写法（停在两轮之间、确认客户端已断开再放行），不放宽期望。

## 2. 改动

- **09a 配置：** `cleanup_enabled`（默认 false，只管新删除）、`cleanup_start` 0.90、`cleanup_stop` 0.80、`retention_min_buckets` 14；生产模板与 `config/production.example.json` 打开滚动删除；应急退出线改为 `cleanup_start`；`verify_resilience.py` 的切换步改为 92%／89%。
- **结构6 建库入口：** `bootstrap_db.py new --name htsg_<x>` 另建一对新库，写 `.local/database-<x>.json`，已存在的名字拒绝。
- **09b 分区与写入（结构第6代）：** 新表 `bucket`（五种状态、`used`、`baseline_wall`、`first_wall`／`last_wall`）；`commit_group`、`observation`、`result`、`state_event` 按 `bucket` 列表分区，主键带桶号。新分区先 `LIKE` 建表再 `ATTACH`，不挡写入。写组时 `FOR SHARE` 读本组的桶：缺桶为 `FAILED NO_BUCKET`，删除中或已删为 `RETIRED`；同一事务里按 D1 改桶状态。
- **09c 维护线程（`htsg/buckets.py`，新）：** 独占线程、每库专用连接；读清单、补缺桶、保持7个待用桶、保存进度、删除、统计、发布快照；每轮的异常写进下一份快照，不结束线程。编号文件写临时文件、强制写盘、原子替换，读不懂时报 `Unreliable`，不当作零。
- **09d 标桶、换桶与路由：** `BucketClock` 在事件循环里按“日期已变、满12小时的运行时长已存盘、下一桶已备好”换桶；重启后接回原桶和它的运行时长。Runtime 启动时最多等5秒拿到可写的桶，超时记 `NONE_READY_AT_START` 照常采集。
- **09e 保留边界基线：** 状态所有者在需要时写一组 `RETENTION_BASELINE`（来源 `_baseline`），落库时记下桶的 `baseline_wall`。
- **09f 删除：** 可删范围从最旧的桶起，到其后第一个带基线、用过的桶为止（该桶保留）；范围内每个桶须已封闭、没有在途组、其后至少有14个用过的已封闭桶（两库合计、同号只算一次），任一不满足整段不删。先标“删除中”，再 `DETACH … CONCURRENTLY` 和 `DROP`；占用率在启动线与停止线之间迟滞；每次删除写管理日志。
- **09g 查询：** 历史查询在每个库里用一个 REPEATABLE READ READ ONLY 事务，排除删除中和已删的桶；结果按库给出“已删除／正在淘汰”和“可能不完整”（基线之前、时钟重叠）；输入依据加 `BASIS_PRUNED` 等标注；回放与导出标出“滚动删除”。
- **09h 自检与报警：** 自检页新增“存储保留与滚动删除”卡片：各库保留的桶与保留边界、最近一次删除、实测删除周期、预计下次删除或不能预计的原因；主库占用持续高于启动线10分钟即报警并给出原因。
- **09i 工具：** `htsg.cli` 的容量估算（每个量每天 69 MB，按终版第13.4节）；`measure.py`、`observe_response.py` 用工作目录里的编号文件；README 存储一节改写。
- **审核 2026-10-29 的修改：** 08-3 库里旧版本的 `EXTERNAL` 路由状态在启动读取时即转为应急并记下；08-2 删去实体盘演练里“路由代码保留供以后扩展硬件”的说法；01-1 控制台不再收到 uvicorn 的启动日志（`log_config=None`，日志只进 `.local/backend.log`）；README 改“合并两库”；实施方案删去移动库的旧说法；`test_capstone_f.py` 删去一行无用代码。
- **评审五条的修复：**
  1. 维护线程停机（`htsg/buckets.py`、`htsg/runtime.py`）：每一步之间、每删一个桶之前都检查停止标记，续删已标记的范围也计入本轮预算，没删完的桶保持“删除中”；`stop()` 返回线程是否真的退出，线程的连接由它自己在退出时关闭；Runtime 停机一开始就调用 `request_stop()`，最后只在8秒期限剩下的时间里等它，结果记在 `health["maintenance_stopped"]`；`tests/conftest.py` 删库前发现残留的维护线程即让测试失败。
  2. 编号文件：`Runtime(..., number_file=...)` 改为必填，正式文件 `.local/bucket_number.json` 只在 `htsg/cli.py` 里指定；测试都改用临时文件。
  3. 首个可用的桶立即发布：读到清单后、每准备好一个桶后都发布快照，不再等整轮结束。
  4. 重试沿用原库：FAILED 和 UNKNOWN 的组都记住原库，重试只发往原库；主库模式下主库缺这一组的桶时在主库等待；只有维护快照确认主库已读到、却一个可写的桶都没有时（`Snapshot.lacks`），才在第一次写入前选应急库；刚退出应急后写主库明确失败、可回退应急库的例外不变。
  5. 输入依据（`htsg/history.py`）：每个库只开一个 REPEATABLE READ READ ONLY 事务，所有查询都排除删除中和已删的桶。
- **Modbus 测试（`tests/test_comm_protocols.py`）：** 新增 `HeldTicker`，第三轮成功后、下一轮发出前停住，停服务器后等客户端报告连接已断开再放行；原有断言一条没放宽。
- **测试：** 新增17个文件（`tests/` 被 gitignore，用 `git add -f` 提交）：test_backend_console、test_bootstrap_new、test_bucket_maintenance、test_bucket_switch、test_bucket_write、test_capacity_estimate、test_partition_scale、test_production_example、test_removed_external_storage、test_removed_point_fields、test_retention_baseline、test_retention_query、test_retention_report、test_rolling_config、test_rolling_delete、test_maintenance_stop、test_retry_target。手工搭的状态所有者改用固定桶（`FixedBucket`）；按旧行为写的用例随新规则改。

## 4. 未做、待定与须现场验证

- **历史查询分区剪枝（方案A，未批准）：** 历史查询只按时间过滤，每条语句都要规划、锁住全部分区。每条语句的规划时间：60个桶约3.5 ms，120个约210 ms，240个420–530 ms，480个830–1230 ms，整次历史查询会超过3秒的语句超时、直接报错；写入不受影响（480个桶时每组中位1.8 ms）。480个桶时一次查询持有约2900个锁，现场锁表名义容量约3840个（60个连接×64），并发查询可能耗尽锁表、波及写库，**涉及红线**。应急库不做滚动删除，每天仍准备新桶，会越积越多空桶。方案A要覆盖12条查询，待出草稿。
- **本机回环卡死，根因未明，涉及红线：** 现场若出现，后端启动时可能卡住；要查清它和杀毒软件、防火墙、端口的关系，以及看守程序能不能发现并重启。
- **残留风险（评审第4条维持终版带来的）：** 主库模式下，如果主库永远补不上某一组的桶，这一组会一直卡在队首，后面的组因队列满被拒、记为缺口。正常情况下维护线程约5秒内补上，没找到会永远补不上的实际路径。是否处理待用户定。
- **待回写终版（先出草稿，逐条批准）：** D1–D8；三个自选阈值（删除周期按间隔超过1小时分段；其他文件按2倍且至少1 GiB；单次删除预算30秒）；维护线程停机语义；第一次写入前“主库无可写的桶”的判定。
- **测量方法：** 容量测量的窗口没有等首次启动的建桶做完，短窗口会把一次性开销外推成全年增长；是否修改 `scripts/verify_resilience.py` 待定。
- **其他待定：** 01-3 启动时应急库不可达会阻塞所有写入，未出草稿；全局横幅与终版第13.3节对不上；修复轮05残留的清理。
- **开发库：** `htsg` 还是第5代，新代码会拒绝它；要用 `bootstrap_db.py new --name htsg_v6` 另建一对新库再切换，删旧库由用户动手。
- **现场：** 滚动删除的实际删除周期、一年容量都只有模拟数据，须现场验证。
