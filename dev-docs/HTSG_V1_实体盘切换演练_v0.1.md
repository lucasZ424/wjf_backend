## 1. 做法

- **三个实例：** `deploy_databases.py install`（输入 `.local/rehearsal/deploy.json`）在 `D:\HTSG-rehearsal\primary`（端口55440）、`C:\HTSG-rehearsal\emergency`（55441）、`E:\HTSG-rehearsal\external`（55442）各建一个 PostgreSQL 实例；连接文件、演练配置和演练用管理员都在 `.local\rehearsal\`，开发用的连接与账户文件不动。`register` 未执行，实例要手动启动（见第3节）。
- **路由按现场规则：** 演练配置是研究配置的生产模式副本（模拟关闭、应急库预留 32 MiB）。脚本只驱动归档路由，不起完整后端，产品代码没有为演练加任何东西。
- **500 MB 预算只在脚本里：** 路由的磁盘读数本来就由外部提供。脚本先读真实路径（盘拔出时这里就报错，与现场一致），再把本次演练数据库的文件大小折算成 500 MB 中的占用。每次运行在三个实例里各新建一个数据库，按部署的做法建好表，不碰以前的数据。
- **每次检查：** 当前写入目标、各盘占预算的百分比；没有一组分散在两个库里，没有不完整的组。

## 2. 结果（2026-10-28，不拔盘）

1. **第一次（01:16）没有写入：** 部署脚本建完实例后没有让它们继续运行（平时靠 `register` 注册的服务），连不上。手动启动后重跑。
2. **第二次（01:17，库 `htsg_rehearsal_20261028_011659`）：** 正常库 475 组（约475 MB）用 47 秒，到 96% 时直接转应急库。原因在演练脚本：新建的移动库没有建表，路由切换前试写移动库报“表不存在”，于是拒用、转应急库。这反过来证明：没准备好的移动库不会被写入。
3. **第三次（01:19，库 `htsg_rehearsal_20261028_011910`，脚本已修）：**
   - 正常库 471 组用 64 秒，**到 95.2% 时转移动库**，符合规则；之后再没有回到正常库，符合“选用移动库后不回正常库”。
   - **E 盘太慢：** 写到移动库的 5 组用了 83 秒（每组约16秒，D 盘约0.14秒），一条写入超过 3 秒语句时限被取消，路由按规则回退应急库。之后每当移动库的试写成功，路由又转回移动库，下一次写入又超时，于是在移动库与应急库之间来回切了 3 次（第477—483组）。“移动库写到 95% 转应急库”这一步因此没有走到，移动库最后只占 3.5%。
   - E 盘日志：5 次“canceling statement due to statement timeout”；一次检查点写约 22 MB 用了 395 秒；没有崩溃或损坏，实例仍在运行。
   - E 盘是一只通用 USB 闪存盘（“VendorC ProductCode”，117 GB）；C、D 盘是 NVMe 固态盘。
   - 三次合计：没有一组分散在两个库里，没有不完整的组。

## 3. 拔盘测试的步骤（暂缓，见第5节）

用户 2026-10-28 决定：E 盘这只 U 盘换成性能更强的移动固态硬盘后再做拔盘测试，本次跳过。换盘后先在新盘上重建移动库实例（见第5节），再按下面的步骤做。

1. **确认三个实例在运行**（重启过电脑就要重新启动），在 PowerShell 里：
   ```
   & "D:\HTSG-dev\pgsql\bin\pg_ctl.exe" -D "D:\HTSG-rehearsal\primary\pgdata" -l "D:\HTSG-rehearsal\primary\pg_ctl.log" -w -t 60 start
   & "D:\HTSG-dev\pgsql\bin\pg_ctl.exe" -D "C:\HTSG-rehearsal\emergency\pgdata" -l "C:\HTSG-rehearsal\emergency\pg_ctl.log" -w -t 60 start
   & "D:\HTSG-dev\pgsql\bin\pg_ctl.exe" -D "E:\HTSG-rehearsal\external\pgdata" -l "E:\HTSG-rehearsal\external\pg_ctl.log" -w -t 60 start
   ```
   已在运行的会提示“another server might be running”，不影响。
2. **开始：** `.venv\Scripts\python.exe scripts\rehearse_storage.py unplug`。先用约1分钟把正常库写到 95%，看到 `writing to EXTERNAL` 后改为每秒一小组，每30秒报一次各盘占用。
3. **拔出 E 盘：** 看到 `writing to EXTERNAL` 后直接拔（“安全删除”会因 PostgreSQL 占用文件而失败）。预期几秒内出现 `writing to EMERGENCY`。若拔出恰在一次提交途中，这一组提交结果不明，按设计只会再问移动库本身，脚本会每秒报一行失败、停在这一组，直到 E 盘回来——这是现行规则下真实会发生的情况，值得观察。
4. **插回 E 盘**（盘符仍是 E:），再执行第1步里 E 盘那一行启动实例（PostgreSQL 会先做崩溃恢复）。预期移动库占用在 70% 以下、绑定检查和试写通过后出现 `writing to EXTERNAL`，继续写。若新盘的小块同步写仍慢，之后可能再次在移动库与应急库之间来回切。
5. **结束：** Ctrl+C。报告写在 `.local\rehearsal\rehearsal-unplug-<时间>.json`。

## 4. 需要你知道或决定的

- **E 盘为什么慢（10-28 实测，用户问及）：** 演练的合成写入每组 2000 行，约 1 MB 表与索引（另有预写日志），在 D 盘每秒约 7 组，约为现场满量（417 行/秒）的 35 倍。用户实测的 22 MB/s 是大文件顺序拷贝；数据库提交是许多 8 KB 小块、每次都强制落盘的写入。同一只 U 盘：64 MB 顺序写（最后落盘一次）9.3 MB/s；8 KB 写入后立即落盘，中位 0.5 毫秒，但最长 493 毫秒，平均只有约 0.22 MB/s（D 盘 1.1 毫秒、约 5.8 MB/s）。检查点那次写约 22 MB 用了 395 秒，也是这种小块写。
- **E 盘作现场移动库余量不足：** 按约 0.22 MB/s 的小块同步写和偶发的半秒停顿，现场满量（约 0.2 MB/s 加预写日志）几乎没有余量，检查点时更会超过 3 秒语句时限。演练里的“写满转应急”在这只盘上走不到；现场的移动库应是外接固态盘或机械盘。拔盘测试用的每秒一小组（约 200 行/秒）低于现场满量，可以顺便看它跟不跟得上。
- **来回切换：** 移动库一次写入失败后，只要下一次试写成功就转回去；慢盘上会反复来回。数据不受影响（没有重复、没有半写），但每次失败都要等满 3 秒，归档吞吐会大降。是否要在失败后先在应急库停留一段时间再转回，是一个设计问题，由你定；本次不改。
- **拔盘恰在提交途中：** 那一组按设计只会再问移动库，移动库不回来，归档就停在这一组（后面的组排在写入队列里，队列满了就拒写、留下缺口）。拔盘测试可以看到这种情况是否出现；是否需要处理，由你定。
- **留下的数据：** 三次运行建的库都留在三个实例里（D 盘约 950 MB），没有删除；实例一直运行到关机。要清理时先停实例（`pg_ctl ... stop`），删不删由你定。
